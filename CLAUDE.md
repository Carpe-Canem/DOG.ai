# DOG.ai

Private, almost fully offline Windows desktop app for running local LLMs. WPF host + Blazor Hybrid UI, .NET 9, maintained in VS 2022. The owner is not reading diffs line by line; explain outcomes in plain language.

**Read `docs/PLAN.md` first.** It has the full feature plan, the milestone table, and a Status section saying what is done and what is next. Update that Status section when a milestone finishes.

**Hand over after every milestone.** One milestone per session. When a milestone is 100% complete (build and tests pass, the app was looked at, the plan's Status is updated, the work is committed), do not start the next one. End with a hand-over to the owner, in this order:

1. Tell the owner to start a new session.
2. Name the model and effort to use for the next milestone (from the plan's "Model / effort" column when it has one; otherwise choose and say why in one line).
3. Give the prompt to paste into the new session, in one fenced block the owner can copy whole. It must stand on its own: the milestone to build and where the plan describes it, the owner's decisions that bear on it, anything this session learned that the plan and `CLAUDE.md` do not already say, and what was left unchecked.

If the milestone is not 100% complete, say what is missing and give no hand-over.

## Commands

```
dotnet build DogAI.sln
dotnet test DogAI.sln
dotnet ef migrations add <Name> --project src/DogAI.Data --startup-project src/DogAI.Data --output-dir Migrations
pwsh tools/walkthrough.ps1      # launch the app on a throwaway data folder and drive it (see below)
pwsh tools/leak-search.ps1      # search folders for marker words and pieces of pictures after a run (its header has the call)
pwsh tools/make-icon.ps1        # rebuild DOG.ai.ico after editing Assets/icon.svg
pwsh tools/make-taglist.ps1 -Source <csv>   # rebuild the bundled picture tag list (see src/DogAI.Core/Images/Tags/README.md)
```

Target is .NET 9 because VS 2022 cannot target .NET 10 (the app itself is `net9.0-windows10.0.19041.0`, which adds Windows Hello; the Debug exe is under `bin\Debug\net9.0-windows10.0.19041.0`). Pin Microsoft packages to 9.0.x. One exception, decided by the owner: `Microsoft.Data.Sqlite.Core` is 10.0.x in `DogAI.Data`, because 9.0.x cannot reopen an encrypted database (see "How locked data works").

## Names

The brand is **DOG.ai** (never "DOG AI"). Code names stay `DogAI.*` (namespaces, project folders); the programs are `DOG.ai.exe` (app and launcher). On disk: data folder `%LOCALAPPDATA%\DOG.ai`, database `DOG.ai.db`, logs `DOG.ai-<date>.log`. Old names are migrated at start (`AppPaths.AdoptLegacyFolder`, `RenameLegacyDatabase`). Do not rename: `DOGAI_*` environment variables, the backup label `"DOG AI"` and the `dogai.db` entry inside backup zips (old backups must restore), the Hugging Face token key `"DOG-AI/hf-token"`, `dogai-engine.txt`, `dogai-image-engine.txt`. The picture engine lives in `engine\images`; a llama.cpp update carries that folder across.

## Rules that must hold

- **Offline.** Never construct an `HttpClient` anywhere. Inject `HubHttp` from `DogAI.Hub`; it refuses unless `OnlineGate` is on and the host is on the allow-list in `OriginPolicy`. The gate is off by default and only the Models section may turn it on. Talking to the local engine on `127.0.0.1` will need its own loopback-only client in `DogAI.Engine`, not `HubHttp`.
- **No external web resources.** No CDNs, web fonts or remote images. Bundle JS/CSS under `DogAI.UI/wwwroot`. The CSP in `src/DogAI.App/wwwroot/index.html` and the filter in `MainWindow.xaml.cs` block anything outside the app origin.
- **Untrusted text.** Imported cards, documents and model output render with raw HTML disabled.
- **`.gitignore`:** the template's `*.app` rule was removed because it hid `src/DogAI.App`. Do not re-add it. The template's `Backup*/` and `*.pubxml` rules would hide `src/DogAI.Core/Backup` and the publish profile, so they are negated at the end of the file.

## Quick-jump, Ctrl+K (M13)

- **What it lists** is `QuickJump` (Core/Search): `Screens` (every page with an address of its own; the Models tabs and Settings categories are built from `ModelsPlaces` and `SettingsCatalog`, so they follow a move by themselves; any other new page needs an entry, and a test checks every address is answered by a `@page`), `Settings` (one target per `SettingsCatalog` entry, with its element as `Anchor`), and the owner's own things from `QuickJumpIndex.LoadAsync` (chats, group chats, stories, characters, shared document collections; read fresh each time the box opens). `QuickJump.Find` orders them: found by name before found by other words; then screens, characters, chats and stories (newest first), collections, settings; every typed word must start a word. Nothing typed lists the five chats used last, then the `Main` screens.
- **Words inside messages** come from the existing search (`ISearchStore`), once three letters are typed (`LooksInMessages`), through `QuickJump.FromHit`; at most `MessageHits` (5), after the name results. Opening one does what the Search screen does (`ChatService.SelectBranchAsync`, then `chat.js` `scrollToMessage`). A setting opens its category and flashes (`scrollToSetting`).
- **The box** is `Components/JumpBox.razor`, in `MainLayout` inside `.shell`. Ids: `#jump`, `#jump-input`, `#jump-list`, results `.jump-item[data-kind][data-route]` (the chosen one has `.on`), `#jump-none`. Arrow keys choose, Enter opens, Escape or a click outside closes and puts the typing back where it was (`chat.js` `jumpOpened` / `jumpClosed`). It does not open over another dialog (`jumpAllowed`: any `.modal-back`). The Search screen has a button for it (`#search-jump`), which asks through `JumpKey` (Core/Search).
- **The key** is caught twice, as Ctrl+L is: `chat.js` `watchJumpKey` in the page and `MainWindow.PreviewKeyDown`. The browser control reports Ctrl keys to the window first, so the window's handler is the one that usually runs (it moves the focus into the page, then `JumpKey.Ask()`); both toggle, and `JumpBox.Toggle` takes two reports within a quarter of a second as one press. Keep both, and keep them toggling: with only "open" on the window's side, a second Ctrl+K never closes the box.
- **Walkthroughs:** `@{ press = 'ctrl+k' }` reaches only the page's listener; `@{ realkey = 'ctrl+k' }` goes through Windows and the window's handler. `realkey` no longer taps Alt when DOG.ai is already in front (the tap put the window in menu mode, which swallowed the next key whenever the page had no focus).
- **Help text** (the rest of idea 4): one line under a control, the rest behind `InfoButton`; warnings and requirements stay visible ("It needs an NVIDIA graphics card", what Cancel deletes). The Documents screen's "How it works" is a `Fold` (`#fold-documents-how`, closed by default).
- **Summaries never think:** `ChatService.SummariseAsync` asks with `Thinking = false` in every mode. A model that thinks first spent the summary's 1,024 tokens on thinking and wrote nothing, so a chat with such a model never got a summary.
- **Small things from the final pass:** `MoreMenu` opens upwards when there is no room below (`chat.js` `placeMenu` adds `.up`; it measures against the nearest part of the page that scrolls), and rightwards when there is none on the left of its button (`.start`, M17 step 6: at 700 px a model row's buttons wrap under its name and the menu was cut off at the left). The Models tabs where fit is judged (Recommended, Browse, Chat models) render only once `ModelsContext.Measured` is true; until then `#models-measuring` shows, because fit judged against nothing reads "Too large for this PC" (the first measure of a run can take ten seconds). A walkthrough that opens Models first must wait for its ids (`#default-general`…). Playhouse's home line (`#home-model`) follows the engine state. `kbd` has a shared style. `.list-head` wraps, so a long button drops under its heading in a narrow list.

## Graphics memory, the search model and downloads (M15)

- **Guests on the card:** `ICardGuest` (Core/Images: `Name`, `HoldsMemory`, `IsBusy`, `LetGoAsync`) is anything besides the chat model and the picture model that can sit in graphics memory. `EmbeddingServer` and `WhisperRecognizer` are the two, given to `CardCoordinator` in `App.BuildServices`. Idle guests are let go (`CardCoordinator.MakeWayAsync`) before a picture sets the chat model aside, when a set-aside chat model comes back and would not fit, and by `ModelLauncher.LoadAsync` when `LoadDecision.WantsRoom` (the model does not fit whole), then the model is judged again; `ModelBenchmark` always asks. A busy guest is never let go. Anything new that holds graphics memory becomes a guest; call `MakeWayAsync` only while holding a card turn.
- **Unload everything** is `ModelLauncher.UnloadEverythingAsync` → `CardCoordinator.ClearAsync`: the chat model through `UnloadByUserAsync` first (before the turn: a loading model holds the turn, and unloading ends it), then under a turn the picture model (`ReleaseAsync`, checkpoint stays chosen) and every guest. It refuses with `BusyReason` while a reply or a picture is being made; the words for the owner are `CardCleared.Text`. Ids in the Models side panel: `#unload-all`, `#unload-all-why` (disabled, with the reason), `#unload-all-note` (what went), `#unload-all-help`, `#card-loaded` (what is in memory), `#card-use`, `#measure-again`. A reply ending raises no event, so `Models.razor` looks at the reason again every second.
- **The document search model** stops after `EmbeddingServer.IdleStop` (2 minutes) and is never stopped while `IsBusy`: a request in progress, or `KeepWhile` (set at start to `DocumentLibrary.IsIndexing`). The Documents panel is `#search-model`, state `#search-model-state[data-state=loading|in|indexing|out]`.
- **Too large can be downloaded:** `DownloadButton` takes `Fit` (not a bool); a too-large one (`.download-btn[data-too-large]`) opens one `Modal` (`#too-large-warning`, `#too-large-cancel`, `#too-large-download`) with `TooLargeDownload.Warning`. The `FitBadge` beside the button is the visible warning: keep it there. Loading is still refused (`LoadDecision`).
- **"Fits beside pictures"** is `BesidePictures` (Core/Models): the coordinator's own rule (`PictureMemory.FitsBeside`) asked ahead of time, for a Standard picture in the largest shape with the checkpoint in use. Card memory is `ModelsContext.CardBytes` (free + what DOG.ai's chat and picture models hold). The chat model's size estimate errs high by 1 to 2.3 GB here, so `ModelLauncher` measures a model two seconds after it loads whole on the card and saves it (`ModelRecord.MeasuredVramBytes` / `MeasuredVramContext`, read with `MeasuredAt(context)`; `MemoryMeasured` makes `ModelsContext` measure again). The chip is `BesidePicturesChip` (`.beside-chip` in `.beside-row`), given `Measured` only for installed models; `#fit-pictures-note` is the line in "How fit is judged". Never mark a model that is not `FitKind.Full`, and none without a picture engine and a checkpoint (`ModelsContext.PictureNeed` is null).
- **Fit badges** count what the picture model holds as free (`FitBudget.From(hw, EngineVram + PictureVram)`): loading a chat model lets the idle picture model go.
- **Walkthroughs:** `#test-picture-result` appears while the picture is still being drawn; wait for `#unload-all` to be enabled (or the note) to know it has finished. `DOGAI_TEST_MIC` with a quiet WAV and a click on `#composer-mic` loads the speech model on the card. A select bound with `@onchange` takes `s.value = …; s.dispatchEvent(new Event("change", { bubbles: true }))`. In the Bash tool a heredoc holding C# with apostrophes can fail to parse: write the script with the Write tool and run the file.

## Images section: Core and storage (M16 step 1)

- **Raw request:** `ImagesDraw` (Core/Images). `Request(prompt, negative, controls)` is the typed text and the controls and nothing else (no quality words, rating words, LoRA triggers, tag check, trimming); `Singles(request)` is one request per picture (a set seed counts up, a new seed is -1 each); `Problems`, `Model` (the controls' VAE, the card's prediction), `Keep` (a `Picture` owned by `PictureOwners.Images`, id `ImagesOwner` = 0), `Like(picture, now)` for "Use these settings" and "Make one like this". Never build an Images request through `ImagePrompt.Compose` or `PicturePrompt`. It still draws only through `IImageEngine` (`CardCoordinator`); `ImageServer` tells `PictureLogFilter` itself.
- **Remembered controls:** `ImagesMemory` (document `images`; singleton, loaded at start). `For(checkpoint, card)` gives `ImagesControls` (each control as the owner left it, else `ImagesControls.StartFor(card)`); `SaveAsync(checkpoint, card, controls)` remembers them. `ImagesSampling` (sampler, scheduler, steps, guidance, clip skip, VAE) is kept per checkpoint and forgotten when equal to the card's; size, LoRAs, seed, hires fix and count are shared. The section's checkpoint is `ImagesMemory.Checkpoint` (`CheckpointAmong(installed, catalog)`: its own, else the Pictures default); choosing it never changes `ImageModelCatalog.Chosen`. LoRAs start unticked (a checkpoint's style LoRAs are not added). **Never put a prompt in this document** (a test checks its fields); the boxes may be held in memory only, as `UnsavedForms` does.
- **Saved prompts:** `SavedPicturePrompts` (document `picture-prompts`; singleton, loaded at start): `SaveAsAsync` (same name replaces, keeps id and mark), `UpdateAsync`, `DeleteAsync`, `SetStartAsync` (one "Start with this" or none), `StartingBoxes(card)` (the marked one, else `FromCard`: quality words before and after, and the negative prompt), `Replace`, `Add`.
- **Previews:** `Picture.Preview` (nullable; a WebP checked by `PicturePreview.Problem`: at most `MaxSide` 512 px and `MaxBytes`, the picture's shape, no metadata; make it at `PicturePreview.SizeFor`). Give it with the picture in `AddAsync` when it can be made first; `SetPreviewAsync` rewrites the whole row (the picture too), so use it only for pictures kept without one. Made in memory, never a file or cache.
- **Pages:** `IPictureStore.PageAsync(PictureQuery.Images(words, checkpoint, shape, skip, take))` gives a `PicturePage` (pictures with previews and without images, `Total`, `HasMore`, `Next`); `CheckpointsAsync` feeds the checkpoint filter. Words are looked for in the prompt only, with SQL `LIKE` (`PictureQuery.WordsOf`, `Matches` is the same rule in C#); the shape is told from the picture's own size (`PictureQuery.Shapes`). `ListAsync` leaves out images and previews.
- **The image is the last column of `Pictures`** (migration `PicturePreviews` rebuilt the table: SQLite walks a large value's whole page chain to reach any column behind it, so with the image fourth every list and search read every picture). A new column on `Pictures` must not be added with `AddColumn` (it would land behind the image): rebuild the table as that migration does (drop the three triggers, copy, carry `sqlite_sequence`, rename, index, triggers again), keeping `Image` last.
- **Overwritten settings are removed data too:** `SqliteSettingsStore.SaveAsync` tells `DatabaseTidy` when it overwrites a document, and `SetPreviewAsync` when it replaces a preview, so the old text or picture leaves the `-wal` file. A new store that overwrites private data in place does the same (`tidy?.Deleted()`).
- `AddAsync` normalises the checkpoint, VAE and LoRA paths (`ImageModelCatalog.Normalise`), so a filter by checkpoint finds every picture.
- **For step 2 and 3 checks:** a real upgrade check needs the previous build: `git worktree add --detach <scratch>\old <commit>`, build it there, run `tools/walkthrough.ps1 -Exe <old exe> -DataDir <folder> -Keep`, then the new build on the same `-DataDir`. Do not print a whole data folder's file list (the WebView2 folder has hundreds of files).

## Images section: Make (M16 step 2)

- **Place:** `Pages/ImagesMake.razor` (`@page "/images"`; the page class is not called `Images`, which would clash with the `DogAI.Core.Images` namespace). A `Modes` entry (navigation in every shell, Playhouse tile, `--c-images`), `Icon` "images", `QuickJump.Screens` "Images" (Main). The Kept pictures tab is `images/kept` (see the step 3 section).
- **In memory only:** `ImagesSession` (Core/Images, singleton, no constructor arguments; a test checks) holds the two boxes, the tries (`ImagesTry`, at most `Max` 32) and a Draw in progress. `Start(() => Saved.StartingBoxes(card))` fills the boxes once per run; `Type` is called on every key. Never give it a store, and never put a box's text in `ImagesMemory`, `AppSettings` or `InterfaceMemory`.
- **Drawing:** `ImagesSession.DrawAsync(engine, ImagesDraw.Model(...), checkpoint, vae, prediction, ImagesDraw.Request(...))` draws `ImagesDraw.Singles` one after another through `IImageEngine` (the coordinator), previews on the copy sent only; Cancel (`Session.Cancel`) keeps finished pictures and the exception still comes out. The page cancels on `Dispose`. `PictureTries` is not used here (it levels requests and uses the card's VAE).

## Images section: Upscale (M16 step 5)

## How the Images section works: the short map (M16, finished in step 6)

- Order of reading: Core and storage (step 1) → Make (step 2) → Kept pictures (step 3) → Helpers (step 4) → Upscale (step 5). The five "Images section: …" sections above keep the rules and ids of each (they were not folded into this map: the ids would have been lost); this is what holds across them.
- **Three places hold things, and only one of them is the disk.** `ImagesSession` (memory only: the two boxes, the helper's sentence, the tries, a Draw in progress); `ImagesMemory` and `SavedPicturePrompts` (settings documents: the controls, the section's checkpoint, prompts the owner pressed Save on); the `Pictures` table (kept pictures with their previews, owner kind `images`). A prompt reaches the disk only inside a kept row or a saved prompt.
- **One path for every picture:** what is typed → `ImagesDraw.Request` (nothing added) → `ImagesSession.DrawAsync` or `UpscaleAsync` → `IImageEngine` (`CardCoordinator`) → an `ImagesTry` in memory → Keep (`ImagesTry.ToKeep` → the page's `KeepRowAsync` → `IPictureStore.AddAsync`). Both tabs and the Upscale dialog go through the page (`ImagesMake.razor`): `PutBackAsync` for Use these settings and Make one like this, `KeepRowAsync` for every Keep.
- **The page reads the session while another thread changes it** (a Draw runs in `Task.Run`). `ImagesSession.Tries` hands out a list that never changes afterwards (a new one per change, made under `_gate`), and a Draw takes its place in one step (`Take`). Seen in step 6: with a plain `List`, a picture finishing while the page drew the strip took the page down ("Collection was modified"). Anything new the page enumerates from the session is handed out the same way.
- **After a save the page shows what was remembered:** `SetAsync` reads `Memory.For` back, so hires numbers nobody set follow a changed step count at once, not only after a restart. A second click on Draw before Cancel has taken its place starts nothing (`_starting`).
- **One place each:** a duration in words is `ImagesPanels.Seconds`; a picture-only WebP is `WebpInfo.PictureOnly` (`PicturePreview.Plain` is the same with `described: false`: only a colour profile may be dropped); text put after what is typed is `SavedPicturePrompts.AddTo` (left out only when the box's last piece already is that text; ending with the same letters does not count); words from a LoRA file are cleaned by `LoraChips` (`ForLora` for the chips; with `max: int.MaxValue`, and `FromFile` for the training tags, for a LoRA's row in Models › On this PC › Pictures › LoRAs, whose editor starts with the words the row shows). The chips are kept per LoRA in the page (`_chips`): cleaning looks each word up in the tag list, and the page renders on every key and every progress report.
- **LoRA file words are sent cleaned** (owner's decision, 2026-11-15; built in M17 step 2): the picture maker and the test picture take a LoRA's card from `ImageModelCatalog.LoraToDraw`, which gives a saved card as it is and, for a LoRA without one, the file's words through `LoraChips.FromFile` (what is shown is what is sent). `LoraFor` still reads the file as it is: use it only where words are shown and counted (the LoRA's row, the chips), never to build a prompt.
- **A hires fix never says "Finishing" half way:** `SdApi.HiresPasses` passes on whatever the engine reports between the first drawing and the second ("decoding") as "upscaling".
- **`PicturePreviews.Down` drops the column with SQLite's own `DROP COLUMN`.** EF's `DropColumn` rebuilds the table, and renaming the rebuilt table fails while the three triggers on other tables name it. Any later migration that touches `Pictures` drops and recreates those triggers, as `Up` does.
- **Leak check** (as in M9 step 9; done plain and locked in step 6): a made-up word in the prompt, the negative prompt and the helper's sentence; pictures drawn, redrawn larger and enlarged that are not kept; the same kept; an upscaled copy of a kept picture discarded (at a size no kept picture has: enlarging the same picture twice gives the same bytes); each picture's `data:` address saved with `@{ eval = "..."; save = '<file>' }`; DOG.ai closed with `@{ close = 1 }`; then `tools/leak-search.ps1` over the data folder, the models folder, the engine folder and TEMP (its header has the call). A plain folder holds the kept words and kept pictures' bytes in `DOG.ai.db` and nothing else; a locked one nothing.
- **A wrong tag correction seen in a helper's notes** gets a test and a tighter rule (`NotASpelling` has "canopy" since step 6: a tree's, not an aircraft's).
- **Words that must stay whole get their own piece.** A ticked LoRA whose file is gone is its name (`.images-lora-name`, cut with an ellipsis) and `.images-lora-gone` ("(not found)", never cut); Workbench's status bar cuts only its first piece (`.status > span:first-child`), so the memory figure stays whole. The kept large view (`.kept-view .modal-body`) is a column in which only the picture gives way, so it fits whatever its facts and buttons take.
- **The winget Vulkan engine's memory steps up once in a long chat** (build 12314; measured in step 6, nothing built for it): when the chat has outgrown the model's room, the oldest messages are left out and the engine reads the prompt again from its changed start, its graphics memory rises once (0.7 GB in a text-only chat, 2.2 GB with pictures in the prompt) and then stays. Twenty pictures of 1,026 tokens before that point leave it flat; the installed CUDA engine never does it (+0.09 GB after 26 pictures). Measure anything about graphics memory on both engines, and for longer than one prompt's worth of chat.
- **Real-engine tests:** `EngineSmokeTests` asks every question with `Thinking = false` and carries a reply on from `RenderPromptAsync(…, thinking: false)` (it asserts no `</think>` in what follows). `PictureInputSmokeTests.A_model_set_aside_while_loading_still_counts_as_seeing` needs the projector beside `DOGAI_TEST_MODEL`. Both pass on both engines; run each class by itself.
- **Walkthroughs (step 6):** one page width per run, and a look pass (six looks, eleven screens each, an enlargement per look) takes about six minutes: start each width as its own background command, since one over ten minutes is cut off. A picture with the hires fix on (`#images-hires-on`, 1280 × 1856 decoded whole, about 17 GB) sets a loaded chat model aside for certain; a plain 832 × 1216 one is borderline with Huihui Q8 loaded. "still running: True" one second after `@{ close = 1 }` is normal for the portable build with a chat model loaded (it is gone within three seconds, with its engines). To see a file "gone", move its hard link to another folder on D: and move it back in a `finally`.

## Settings in pictures (M18 step 3)

- **What the scene planner is told** besides the passage and the people is a `SceneContext` (Core/Images/PictureWriter.cs: `Source` story or chat, `Setting`, `Before`, `LastPlace`), written by `PictureWriter.SceneBlocks` in this order, each with room of its own: "Setting: where the story takes place. It is to be drawn…" (`MaxSettingLength` 2,500), "What happened just before (it tells where they are)" (chats: "What was said just before…"; `MaxBeforeLength` 1,500, cut from the start by `CutStart` so the end stays), "The last picture of the story took place in: …". The old "Background, for understanding only (do not draw it)" is gone; `SceneAsync` takes `context:`, not `background:`.
- **Stories:** `Illustrations.Context(story, path, passage)`: `Setting` (World box, then premise), `Before` (the end of the passage before this one on the path, then the reader's action or the author's direction as typed), `LastPlace` (the nearest earlier passage on the path whose picture has a place; never the passage's own). `StoryThread` passes its `Path`.
- **Chats:** the card's Scenario is no longer inside "about" (it was cut at 500 characters after a long description): `ChatPictures.People` puts it, filled in, on `IllustrationPerson.Setting`, and `ChatPictures.Setting` makes the block (one character: the text alone; a group: "Ann and Bo: …", the same text once), then the chat's summary only while `SummaryThroughId` is on the path before the reply. - **The form:** a scene's place line asks for the place first, then indoors or outdoors, then what is seen, from the setting when the passage does not say; the schema allows `PicturePlace.MaxWritten` (6), the prompt keeps `MaxPlace` 5 and `MaxLight` 3. `PictureScene.PlaceAndLight()` moves a place word that is a light word (in the light list, or `PicturePlace.IsLightWord`) to the light; `PicturePrompt.SplitPlaces` makes an unknown two-word place of two tags into both ("forest floor" → forest, floor; tags only). The people line says only people the passage itself shows (with the "before" block the planner added someone from the passage before; still 1 of 3 in the smoke run). ## Thinking budget (M18 step 4)

- **Levels, not switches:** `ThinkingLevel` (Core/Chat/ThinkingLevel.cs: Off, Short 512, Normal 1,536, Long 4,096, NoLimit; saved as its number, so keep the order). `ChatOptions.General` / `Roleplay` (`LevelIn(mode)`, `SetGeneralAsync`, `SetRoleplayAsync`) and `StoryOptions.Level` (`SetLevelAsync`). Settings has three lists: `#general-thinking`, `#roleplay-thinking`, `#story-thinking` (inside the anchors `#set-…-thinking`; the line under each is `#…-thinking-blurb`). They start at General No limit, the other two Short (owner's decision, 2026-11-15).
- **Old settings are read, never rewritten:** `AppSettings` keeps the levels nullable (`GeneralThinkingLevel`, `RoleplayThinkingLevel`, `StoryThinkingLevel`). Read them only through `ThinkingLevels.General(settings)` / `Roleplay` / `Story`: with no level, General follows its old switch (`AppSettings.GeneralThinking`: on is No limit, off is Off) and the other two are Short whatever their old switches said (those two properties are gone). A backup from before M18 restores the same way for the same reason. A number that is no level counts as none.
- **On a request:** `ThinkingLevels.Apply(preset, level)` (what `ChatOptions.Apply` and `StoryOptions.Apply` call). Off sets `Thinking = false`. Any other level sets `ThinkingControl` and, with a limit, `ThinkingBudget` (both `[JsonIgnore]`, like `MaxTokens`); `LlamaApi.ChatRequestBody` sends them as `thinking_budget_tokens` and `reasoning_control: true`. Never send `reasoning_budget_message`: no words are added at a cut (owner's decision). A request with `MaxTokens` (choices, a rewrite, the story plan draft) thinks at most as long as its answer may be, at any level, and `MaxTokens` grows by that budget so the answer keeps its room: set `MaxTokens` before applying the level.
- **Answer now:** a request with `ThinkingControl` gets the engine's name for the reply as its first piece (`ChatDelta.ReplyId`). `ActiveReply` keeps it and counts thinking pieces (one piece is one token; the engine gives no count): `ThinkingTokens`, `ThinkingBudget`, `IsThinking`, `CanAnswerNow`, `AnswerNow`. `ChatService.AnswerNowAsync` → `IChatEngine.EndThinkingAsync` (a default that says `NotSupported`; `EngineManager` → `LlamaApi.EndThinkingAsync`, `POST v1/chat/completions/control` with `reasoning_end`; it takes no card turn and wakes nothing). Ask the model through `ChatService.AskAsync(active, prompt, preset, ct)` so the count knows the budget; code that reads the pieces itself calls `active.Track(delta)` (the choices step). The button is `Components/Chat/AnswerNowButton.razor` (`#answer-now`; shown only while the reply thinks), beside Stop in `ChatComposer` and in the story rewrite dialog. Stop still stops everything.
- **What a reply keeps:** `ThinkingFacts` (tokens, budget, now, refused: numbers only) as `thinking` in `ChatMessage.ExtraJson`, through `StoryTurn.Thinking`, written once when a new reply is saved (`GenerateAsync`). Everything that rewrites a message's `ExtraJson` reads it fresh as a `StoryTurn`, so it stays (choices, a kept picture).
- **The choices step redraws nothing by itself** (it streams no text): `ChoicesAsync` raises `Changed` when `CanAnswerNow` or `IsThinking` turns, or Answer now never shows there (found in M18 step 5: the choices of an adventure at No limit took 30 s with no button). A new request that streams without `StreamAsync` does the same.
- **The notes:** `ThinkingCut.Of(message)` → `ThinkingCutNote.razor` (`.thinking-note[data-cut=budget|now|engine]`, right under `details.thinking`; `MessageView` takes `Cut` and `ThinkingLabel`, `StoryThread.Thinking` the same). The engine marks no cut in the stream, so "cut at its limit" is told from the count: within `ThinkingLevels.CutMargin` (100) of the budget, except for a reply stopped while it still thought (no answer and no speed figures: Stop at 450 of 512 is not a cut). More than that past the budget, or Answer now refused, is an engine too old for the fields: the note says to update it in Models › Engines, and nothing else is built for it (owner's decision). While a reply is written only "now" and "engine" show (`ChatThread.LiveCut`). The heading while thinking is `ThinkingLevels.Counter` ("Thinking… 1,200 / 1,536"; no limit: "Thinking… 1,200"). `ThinkingOnly` has the reason `Cut` (no answer after a cut).
- **Tests:** `ThinkingBudgetTests.cs`. The fake engine that thinks until Answer now reaches it is `ChatServiceTests.Thinker` (it sets `FakeEngine.Reply` and `FakeEngine.EndThinking`); a `FakeEngine` without `EndThinking` is an engine too old.
- **Walkthroughs:** a list on the Settings page takes the `change` event (`s.value = …; s.dispatchEvent(new Event("change", { bubbles: true }))`). `#answer-now` appears with the first thinking piece and goes about 0.15 s after it is pressed. With Huihui Qwen3.5 9B a reply at Short takes 9 to 20 s and its count stops at 485 to 495 of 512; at No limit a character reply thinks 2,500 to 4,000 tokens. ## How the looks work

Three skins (`workbench` default, `fireside`, `playhouse`), each in dark and light. State is `AppearanceState` in Core; the choice is saved in settings.

- `MainLayout.razor` puts `skin-<id>`, `data-theme` and `data-screen` on the root and picks a shell component (`Layout/*Shell.razor`).
- Pages do not know which skin is active. They fill named regions with `<SectionContent SectionName="...">`: `title`, `list`, `composer`, `aside`. The page body is the main area. Empty regions collapse via `:empty`, so keep outlet wrappers free of whitespace.
- **A page that fills regions declares no variable at its top:** no `@if (_x is { } x)` or `out var` in a top-level `@if`, and no top-level `@{ }`. Test the field (`_x is not null`) and declare the variable inside the block. Such a variable belongs to the whole page; once a handler uses it, the compiler hangs every lambda of the page off an object made anew on each render, and `SectionOutlet` keys a region's content by its lambda, so title and composer are rebuilt on every render (the Images page's prompt boxes lost the focus after every key; found after M16). `ChatPanelTests` checks every `.razor` with a `<SectionContent`. A script `input` event does not show it: check typing with a `mouse` step, then `type` one letter at a time, and read `document.activeElement`.
- `app.css` has three parts: tokens per skin/theme, shared components that use only tokens, and per-skin layout overrides. New screens should need only shared components; add per-skin overrides sparingly.
- Fireside uses a serif (`--read`) for reading text. Playhouse has a home screen at `/` and a colour per mode; the other skins redirect `/` to `/general`.
- In `.razor` `@code`, avoid switch-expression arms that start with `<` (Razor parses them as tags).

## How chat works

- Chat logic is `ChatService` in Core. It talks to the model only through `IChatEngine`, so tests use a fake engine with the real SQLite store.
- Messages are a tree (`MessageTree`). Regenerate and edit add a sibling and move `Conversation.ActiveLeafId`; nothing is overwritten.
- Model output goes through `MarkdownRenderer` (Core), which disables raw HTML and neutralises non-web links. Never render model text with `MarkupString` any other way.
- Speech colours: `MarkdownRenderer.Render(..., speech: true)` wraps quoted lines in `span.say` and marks actions `em.act` (character chats, group chats and stories; never General). Colours are the `--say`, `--act` and `--say-1…6` tokens in `app.css`; a group member's colour is the `tone-N` class from `SpeakerInfo.Tone`. The switch is `AppearanceState.SpeechColours` (Settings, Reading).
- UI needs from Windows (file dialog, clipboard) go through `IDesktopShell`, implemented in App.
- General and Characters share `Components/Chat/` (`ChatThread`, `ChatComposer`, `StylePanel`, `MemoryPanel`, `PromptInspector`); Story reuses the composer and the panels. Character chats run through the same `ChatService`; `CharacterPrompt.Layout` (Core) turns card, persona, lore, author's note and memory into a `PromptLayout`, and `CharacterCard` reads and writes card files. Styles come from `PresetCatalog`, not `SamplerPresets` directly.
- A prompt is a `PromptLayout`: system-message parts (each with a drop order for when space runs out) plus text placed inside user turns. Never add a `system` message after the first one; many chat templates reject it. Notes go into user turns via `PromptLayout.Arrange`.
- Lore lives in the card's `character_book` inside `Character.ExtraJson`; edit it through `Lorebook` (`For`, `SaveTo`) so unknown fields survive export. Keys from cards are untrusted: matching uses a regex timeout.
- Group chats are `Mode = "group"` conversations with members in `ChatMembers` (`IChatStore.GetMembersAsync`/`SetMembersAsync`) and each reply's writer in `ChatMessage.SpeakerId`. Who speaks is `GroupTurns` (Core); the speaker's prompt is `CharacterPrompt.GroupLayout`. In `BuildPromptAsync` group history is name-prefixed and same-role turns are merged, and the layout's `Directive` ends every group prompt with a user turn: keep roles alternating. The page is `Pages/GroupChat.razor`; side-panel settings shared with one-to-one chats are `Components/Chat/RoleplayPanels.razor`.
- DOG.ai's own model jobs (summaries, card builder) set `MaxTokens` / `JsonSchema` on a copy of a preset; both are `[JsonIgnore]` so they never end up in a user's saved style. Check their output before keeping it (see `CharacterPrompt.IsUsableSummary`).

## How stories work

- A story is a `Mode = "story"` conversation plus a `Story` row (`IStoryStore`): kind (interactive or authored), bible, outline, dice and state switches. Passages are replies in the normal message tree; the user turns are the player's actions (interactive) or the author's directions (authored). Per-message story details (choices, state, dice roll, chapter) are JSON in `ChatMessage.ExtraJson`, read and written through `StoryTurn`.
- Story logic is the `ChatService.Story.cs` partial and `DogAI.Core/Stories`: `StoryPrompt` (layout, `ForPrompt`, choices schema and parsing, revision prompt), `StoryBuilder` (AI bible draft), `BranchMap`, `StoryExport`. `StoryPrompt.ForPrompt` rewrites user turns for the model (dice result, "write the next passage of chapter N"); the saved turns stay as typed.
- Interactive passages take two requests: prose first, then the same prompt plus the passage with a JSON schema for choices and state (`ChoicesAsync`). Rules the model must not forget (length, dice, state) go in `PromptLayout.FinalInstruction`, next to the newest user turn.
- Character cards in a story are links, not copies: `Story.Characters` (a JSON list of `StoryCharacter`: card id plus `Main`, the card the player plays). `ChatService.StoryCastAsync` reads the cards for every passage and `StoryPrompt.Layout` adds them as a `Cast` part, their examples and the lore that fired (`StoryCast.cs`). A card's own system prompt and post-history instruction are not used in stories. `SqliteCharacterStore.DeleteAsync` takes a deleted card out of stories. `story/new?character=<id>` (the **Start a story** button) preloads a card; `StartStoryAsync(..., opening)` saves a card's greeting as the first passage of an adventure.
- The opening passage has no parent; `PromptLayout.OpeningTurn` supplies the user turn chat templates need before it.
- Per-line speakers: `Quotations` (Core/Text) finds quotations with the same rules for rendered HTML and plain text; `SpeakerGuess` pins each one to a person or to nobody (it reads a passage paragraph by paragraph, in order, and resolves "she said" through each card's `Pronoun`; one instance per passage). The people are `StoryPrompt.People`: the cards in cast order, then names from the bible's Cast box with no colour or voice. `MarkdownRenderer.Render(..., speakers)` adds `tone-N` to a pinned `span.say`; `SpeakerTones.Of` gives a character's tone (stories and group chats). Reading aloud takes a `VoiceCast` (`ReplyVoice.CastForAsync`); `VoicedPieces` cuts a passage into lines per voice. Change quote rules only in `Quotations`, so colour and voice keep agreeing (a test checks).
- Story requests (passages, choices, rewrites, the bible draft) go through `StoryOptions.Apply`, which gives them the story's thinking level (Off sets `SamplerPreset.Thinking = false`; any other level a budget, see "Thinking budget (M18 step 4)"); `LlamaApi.ChatRequestBody` turns Off into `chat_template_kwargs` and a budget into `thinking_budget_tokens`. New story requests must use it too. A story's summaries never think, whatever the setting (see "Quick-jump, Ctrl+K (M13)").
- A character chat becomes an adventure through `ChatService.StoryFromChatAsync` (copies `MessagesForStory` of the shown branch and the summary; the chat is not touched). The page is `story/new?chat=<id>`.
- In UI code the name `Story` is the page class inside `Pages/Story.razor`; the pages alias the model as `StoryInfo`. Components are in `Components/Stories/`. Selecting text for a rewrite is reported by `wwwroot/js/story.js` and matched back to the markdown source with `TextSpan.Find`.

## How documents work

- Core: `DogAI.Core/Documents`. `TextExtractor` reads PDF (PdfPig), .docx (zip + XML, DTDs refused) and text/code; `Chunker` cuts passages (~800 chars, page and heading kept); `Retriever` merges vector and BM25 rankings; `DocumentLibrary` adds files, indexes in the background, searches, and recalls messages. Storage is `ICollectionStore` (`SqliteCollectionStore`).
- Every document belongs to a collection. A chat's own files are a collection with `ConversationId` set (hidden from lists, deleted with the chat); shared ones are attached through `ChatCollections`.
- The search model is `IEmbedder`, implemented by `EmbeddingServer` (Engine): a second llama-server with `--embedding`, started on demand and stopped after two idle minutes or when the card needs the room (see "Graphics memory, the search model and downloads (M15)"). ## How image understanding works (M17 step 2: Core, storage and engine; step 3: Models)

- **A picture on a message** is an `AttachedPicture` row (Core/Chat/AttachedPictures.cs; table `AttachedPictures`, store `IAttachedPictureStore` / `SqliteAttachedPictureStore`): not a `Pictures` row (those are drawn pictures with their settings). It goes with its message (a foreign key that cascades; `SqliteChatStore.DeleteAsync` also deletes by chat). `IChatStore.GetMessagesAsync` fills `ChatMessage.Pictures` (not a column; rows without their images), so everything that has a message knows its pictures. **`Image` is the last column**, as in `Pictures`: a later column is not added with `AddColumn` (rebuild the table, keeping `Image` last; a test checks the order).
- **What may be kept or sent is one thing:** `AttachedPictures.Problem(bytes)` (null = fine): a whole JPEG by its own structure (`JpegInfo.Read`, Core/Images: every part walked, nothing decoded; baseline or progressive, 8 bits, grey or colour, nothing after its end), at most `MaxSide` 1,024 px and `MaxBytes` 2 MB, with no EXIF, XMP, comment, thumbnail or unknown part. `AttachedPictures.Plain` takes out only the colour profile the browser's encoder adds; a file with a description is never cleaned quietly, it is refused (as previews are). The store checks on `AddAsync`, and `LlamaApi.Checked` again on every send. Step 4's page makes the JPEG (`SizeFor`, `Quality` 90); Core never opens a foreign file.
- **Sending:** `ChatService.SendAsync(id, text, pictures)` (at most `MaxPerMessage` 4; text may be empty; refused for stories) and `EditAndResendAsync(id, messageId, text, keep, added)` (the edited question gets copies of the kept pictures: `CopyAsync`, the very bytes). Nothing is stored when a picture is refused.
- **The prompt:** `PromptMessage.Pictures` is a list of `PromptPicture` (id, the stored JPEG, size, `After` = how many characters of the turn's text come before it). A message's pictures come first in it; `PromptLayout.Arrange` moves them back when it puts passages in front; a joined group turn keeps each picture before its own message's text. `LlamaApi.Content` writes text pieces and `image_url` parts holding `data:image/jpeg;base64,` + the stored bytes; **there is no other kind of part, and never an address** (the engine fetches addresses, and starts `ffprobe` on bytes it cannot read). A turn without pictures is a plain string, byte for byte as before.
- **A model that cannot see** (`IChatEngine.SeesPictures` false) gets `AttachedPictures.UnseenNote` once per picture at the start of the message's text, and the reply's `StoryTurn.Unseen` (JSON `unseen`) says how many: step 4's "The model could not see this picture" reads it. Text-only jobs (summaries, recalled messages, `ChatExport`, `StoryFromChatAsync`) use `AttachedPictures.TextOf(message)`: "[picture]" per picture, then the text. A new text-only job does the same.
- **Counting:** the chat template is given text only (`LlamaApi.ApplyTemplateAsync` drops pictures). `ChatService.RenderAsync` puts a mark of its own where each picture is (`PictureMark`, a new one every run), finds the marks in the rendered text, and gives back `Shown` (the inspector's text, with `AttachedPictures.Marker`: "[picture 1,024 × 640, 642 tokens]"), `Raw` (no marks: what is counted, and what a raw completion carries on from) and the pictures placed in `Raw`. Tokens = text + each picture's cost: `IChatEngine.CountPictureTokensAsync` (`POST /v1/messages/count_tokens`, with the picture less without; asked only while the model is in memory and sees, never waking one; kept per picture id until the model changes), else `AttachedPictures.TokensByRule` (round(w ÷ 32) × round(h ÷ 32) + 2, the Qwen3.5 family's rule). When the oldest messages are weighed no image is read (the remembered count or the rule). Images are read only for the pictures that go into the prompt and held only while the reply is written (`_pictureImages`, cleared in `End`). For step 4's meter: `ChatService.PictureTokens(picture)` and `CountPictureAsync(jpeg)`.
- **Carrying a reply on** (Continue; not Write mine, which sends no picture since step 6: see the short map) with pictures uses `IChatEngine.StreamCompletionAsync(prompt, pictures, …)`: `LlamaApi.CompletionPrompt` sends `{ prompt_string, multimodal_data }` with the engine's own marker (`media_marker` from `GET /props`, a new one at every start) where each picture is. A plain string prompt with the marker in it is not enough: the engine then ignores the pictures.
- **Too much for the context:** the engine cuts nothing and answers 400 `exceed_context_size_error`; `LlamaApi.ErrorText` turns it into `ContextBudgeter.TooLong(needed, room)`. The newest message always goes in, so four pictures at 4,096 tokens end there.
- **The projector:** `ModelProjector.Find(modelPath, info)` (Engine): a `.gguf` with "mmproj" in its name at the top of the model's own folder whose header says `general.type = mmproj`, `clip.has_vision_encoder` and `clip.vision.projection_dim` = the model's `EmbeddingLength`; of several, `Projectors.Pick` (Core/Models: F16, BF16, Q8_0, any other, never F32). Never a saved path. It is loaded whenever the model has one (owner's decision): `ModelLauncher.DecideAsync` puts it in `LoadDecision.Projector`, `EngineOptions.Projector` carries it, `EngineManager.Arguments` adds `--mmproj <file> --image-max-tokens 1024` (never `--media-path`, `--mmproj-url`, `--mmproj-auto`). Without a projector the switches are exactly those of before M17 (a test pins the list). `EngineManager.SeesPictures` is `modalities.vision` from `/props` and stays true while the model is set aside.
- **If the engine stops with the projector** (too old for the switches, or a projector it cannot use), `EngineManager.LoadAsync` loads the model again without it and sets `PictureInputProblem` (also logged). On this PC › Chat models shows it on the model's row (`#picture-input-problem`).
- **Fit and memory:** `ModelShape.ProjectorBytes` → `FitEstimator` adds `Projectors.Need` (file size + 0.25 GB) to the working memory, on the card whole. Build a shape for an installed model with `info.ToShape(size, projector?.SizeBytes ?? 0)` (`LibraryTab`, `ModelLauncher`, `ModelBenchmark` do; the download lists count the projector offered with a version: see the next section). `ModelRecord.MeasuredVramProjector` says whether the measurement was taken with the projector; read it only through `MeasuredAt(context, withProjector)`.
- **Tests:** `AttachedPictureTests` (the JPEG check, the store, upgrade, lock, backup and restore, portable, removed data), `ChatServiceTests.Pictures.cs` (the fake engine has `Sees`, `CountPicture`, `Rendered`, `Counted`, `PictureCompletions`), `PictureInputTests` (request bodies, the projector rule, fit, the LoRA words), `PictureInputSmokeTests` (the real engine: runs when `DOGAI_TEST_MODEL` has a projector beside it; `DOGAI_TEST_OTHER_MODEL` = a small model the projector does not belong to, the embedding model will do). `TestJpegs.Make(width, height, …)` writes a JPEG that is whole as far as its structure goes (all DOG.ai reads); `TestJpegs.Real(…)` are three real files in `tests/DogAI.Tests/Pictures` for the real engine (made with System.Drawing; a font size there is in points at 150 %: give it in pixels, or the word runs off the picture and the model, rightly, reads "WOO").
- **Checks without a screen:** a scratch console program that references `DogAI.Core` and `DogAI.Data` can open a locked throwaway folder (`LockFile.Read(paths.LockFile).OpenWithPassword(…)`, then `AddDogData` with a `DatabaseKey`) and put a picture on a message with `IAttachedPictureStore.AddAsync`; the app then answers about it. Run real-engine test classes one at a time (`--filter`): xUnit runs classes side by side, so two models are on the card at once (an existing text-only engine test failed once that way and passed alone).
- **Editing files from the Bash tool:** a Python script in a heredoc fails to parse when the C# in it has apostrophes, and `\n` inside it becomes a real line break. Write the script with the Write tool and run the file, or use Edit.

## Pictures in chats (M17 step 4)

- **Which chat boxes take pictures:** `ChatComposer` takes them only where the page passes `OnSendWithPictures` (an `EventCallback<ChatInput>`: text and JPEGs): General, Characters, GroupChat. Story keeps `OnSend(string)`, so it has no button and no paste or drop handler (a test lists the three pages). Pages call `ChatService.SendAsync(id, input.Text, input.Pictures)`.
- **The page opens files, never C#:** `wwwroot/js/attach.js` (`watchPictures`, `choosePictures`), imported by the composer only where it takes pictures. It tells the kind by the file's first bytes (PNG, JPEG, GIF, BMP, WebP; never the name or type, so SVG and renamed text are refused), decodes with `createImageBitmap(file, { imageOrientation: 'from-image' })` (a phone photo is turned upright, a GIF gives its first frame), draws on white (`alpha: false`, white first: a see-through part would be black) at most `AttachedPictures.MaxSide` on the long side, and writes a JPEG at `AttachedPictures.Quality`. Files over `ComposerPictures.MaxFileBytes` are refused unread. Paste takes files only when the clipboard has no text (text copied from a document often carries a picture of itself). A drop outside the box is cancelled on the whole page by `chat.js` `guardDrops`, which `LinkGuard` (always in `MainLayout`) puts in place when the page starts, so it holds on every screen (step 6: it used to be in `attach.js`, so Playhouse's home screen had none); without it the browser control would try to open `file:///…` and the refused address, with the file's name, would be noted in the log. The chat box's own `dragover` / `drop` handlers stop the event before it gets there; any new drop target must do the same. A batch of pictures always ends with `PicturesDone` (a `finally` in `take`), or the box would wait with Send off.
- **The composer's side** (memory only): `PicturesOffered(count)` answers how many more fit (0, with the line, when `Engine.SeesPictures` is false), `PictureArrived(bytes)` runs `AttachedPictures.Plain` and `Problem` and keeps the JPEG with its `data:` address made once, `PicturesDone(refused, leftOut)` says what was refused or left out. Each picture is counted by `ChatService.CountPictureAsync` (the engine while a model that sees is in memory, else the rule), again when the model changes. The pictures leave the box with the text on Send (hands-free sending takes them too), on leaving the page, and when another chat opens in the same page (`OnParametersSet` compares the chat of `Path`: General keeps one box across chats, and pictures for one chat must never be sent to another); never written anywhere.
- **The button** (`#composer-attach`, the "images" icon) shows only while `Engine.SeesPictures` (the engine's own word, so a projector that arrives while a model is loaded counts from its next load), or while pictures wait; disabled at `MaxPerMessage`. The composer listens to `Engine.Changed` itself. Ids: `.composer-box` (the drop target, `.dropping` while files are over it), `.composer-file` (the hidden file input), `#composer-pictures` with `.composer-picture[data-n]` and `.composer-picture-remove[data-act=remove]`, `#composer-pictures-working`, `#composer-pictures-help` (`ComposerPictures.Help`), `#composer-pictures-note` (with `#composer-pictures-note-close`), `#composer-send`, `#composer-meter`, `#composer-meter-text`, `#composer-room`.
- **Wording and the meter's rule** are `ComposerPictures` (Core/Chat): `CannotSee(loaded)` and `WaitingUnseen` are `PlaceLine`s (text, `ModelsPlaces.LibraryName`, its address; the page makes the name a link), `TooMany`, `Refused`, `Unseen(n)`, `Help`, `Judge(context, used, pending)` → `PictureRoom` (`TooLarge` when the pictures alone exceed `MessageRoom` = context less `ContextBudgeter.ReplyReserve`: four at 1,026 do at 4,096; `OlderLeftOut` when the chat and the pictures do), `RoomLine`, `MeterPart`. While pictures wait, the meter's figure and `Judge` use `ComposerPictures.NextPrompt` (the last reply's prompt and answer without its thinking, from `ThinkingOf`: `StoryTurn.Thinking.Tokens`, else the reasoning's length ÷ 4), because thinking is never sent again; with nothing waiting the meter is as before (prompt + completion). It shows while pictures wait even in a new chat.
- **On a message:** `Components/Chat/AttachedPictureView.razor` holds the branch's pictures as `data:` addresses (read once per id through `IAttachedPictureStore.ImagesAsync`, one load at a time, let go with another chat) and owns the large view (`Modal` `.attached-view`: `#attached-large`, `#attached-prev`, `#attached-next`, `#attached-meta`). `ChatThread` draws the small ones in `MessageView.Above` for the owner's messages (`.msg-pictures[data-pictures]`, `.msg-picture[data-attached]`); a message of pictures alone has no empty bubble. A reply's `StoryTurn.Unseen` is `.unseen-note[data-unseen]` in `Below`, before its sources (it counts every picture before the reply that the model was only told about).
- **Editing a question with pictures:** the edit box lists them (`#edit-pictures`, `.edit-picture[data-attached]`, `[data-act=remove|keep]`, `.removed`); Save (`#edit-save`, disabled when nothing changed or nothing would be left) calls `EditAndResendAsync(…, keep, null)`. - **Walkthroughs:** the attach button opens Windows' Open dialog: `@{ mouse = '#composer-attach' }`, then `@{ dialog = '<full path>'; title = 'Open' }`; for several files, a second dialog takes `'"a.jpg" "b.gif"'` (names in the folder the first one opened). **A real paste** needs Windows' focus in the box: `@{ osclick = '.composer textarea' }`, then `@{ realkey = 'ctrl+v' }` (a `mouse` click does not give it, and nothing arrives). ## How image understanding works: the short map (M17, finished in step 6)

- Order of reading: Core, storage and engine (step 2) → Models (step 3) → chats (step 4) → Images and General (step 5). The four sections above keep each step's rules and ids; this is what holds across them.
- **A picture from outside is in at most three places, and only one is the disk:** the chat box (`ChatComposer._pending`, memory), the helper (`ImagesSession.Looked`, memory), and a message (the `AttachedPictures` table). Everywhere it is the same thing: the JPEG the page made (`attach.js` `toJpeg`), made plain and checked by Core (`AttachedPictures.Plain`, `Problem`). The owner's file is opened only by the page; no byte of it is kept.
- **One path to the model:** the stored bytes → `PromptPicture` → `LlamaApi`, which has three shapes and no fourth: `PicturePart` (`image_url` with `data:image/jpeg;base64,`) in a chat request, `CompletionPrompt` (`multimodal_data`) for a reply carried on, `CountedPicture` for counting; each goes through `LlamaApi.Checked`. Summaries, planners and every other text-only job get `AttachedPictures.TextOf`.
- **Write mine sends no picture** (step 6): `BuildPromptAsync` with `PromptEnd.UserTurn` leaves the pictures out and puts nothing in their place (a message that is pictures alone becomes `AttachedPictures.PictureOnly`). ## How video works (M20 step 2: Core, storage and engine; no screen yet)

- **Core** is `DogAI.Core/Video`. `VideoRequest` stands beside `ImageRequest` and shares nothing with it: the sentence, the fixed English negative prompt (`FixedNegative`: says nothing about style, so a drawn first frame stays drawn), size, seed, `Decoder` (Fast or Own, carried apart from the size), `StartFrame` (bytes), and the trial's numbers as defaults (121 frames, 24 a second, 20 steps, Euler, guidance 5, flow shift 5, compression 70). `VideoRequest.For(sentence, quality, shape, seed, startFrame)` is the owner's clip: Quick = `PictureLevels`' Small sizes with the fast decoder, Better = the Normal sizes with the model's own. `Problems()` refuses a side that is no multiple of 32 (the engine rounds up), frames that are not 4n + 1 or more than 121, and a bad first frame.
- **The first frame** is checked by `VideoStartFrame.Problem(bytes, width, height)`: a WebP without EXIF or XMP (what DOG.ai draws) or a JPEG without profile or extras (what the page makes: run `AttachedPictures.Plain` first), 64 to 4,096 px, **of the clip's shape within 5%** (`SameShape`: every DOG.ai size of one shape goes with every clip of that shape; the engine then takes a sliver off two edges). Any other shape is refused: the engine would cut the middle out, so the page cuts first (step 4). A JPEG for a Better clip may be larger than `AttachedPictures.MaxSide`: the chat picture's limits do not apply here.
- **Make a clip only through `IVideoEngine` from the app's services**, which is `CardCoordinator` (as `IImageEngine` is). `CardCoordinator.MakeAsync(model, request, progress, ct)`: the request and the model's files are checked before anything moves (`VideoModel.Problem()`), a card `VideoMemory.CardCanMake` says cannot hold the clip is refused at once (since M20 step 4: see "Video: Make"), then **under one turn** the chat model is set aside (a reply being written is waited for), the picture model is let go, every idle guest is let go (a busy one stays), the card is measured again and a clip is refused in words when less than `VideoMemory.Need` (15 GB Quick, 16 GB Better) less `CardSizeSlack` is free (`RoomEnough`); an unmeasurable card goes ahead. The chat model comes back as after a picture: when it is next asked for. `IsMakingVideo`, `BusyReason` ("A video is being made…"), `InMemory` ("the video model") and the idle lock (through `IsBusy`) know about a clip.
- **The video program lives for one clip** (`VideoServer`, Engine/Video; the picture engine's own `sd-server.exe`): started for the clip, ended in a `finally` when the clip was collected, cancelled or failed. So the decoder (decided by the engine at start) is always the one asked for, nothing stays on the card, and a cancel is: ask the engine, wait `SdApi.VideoCancelWait` (3 s), end the program (2.2 s measured; the model's own decoder cannot be interrupted any other way). The price is known: every clip is the first clip of a fresh program, about 3 s more, and **the card peaks at about 23 of 24 GB while the clip is decoded** (the engine takes what the cleared card has, up to the total less the 3 GB of `--max-vram -3`; shared memory stayed at 0.1 GB and nothing slowed down in thirteen clips). `VideoServer.LastMadeAt` is for the estimate's `warm`.
- **Start switches** are `VideoServer.Arguments(model, decoder, port, blankPage, plan)`; `VideoServerTests.Both_programs_start_switches_are_pinned` holds both programs' lists whole (a picture's as before M20). `--taesd` is always there (previews), `--taesd-preview-only` only for the model's own decoder. Never add `--offload-to-cpu`, `--mmap`, `-m`, a LoRA or upscaler folder; never remove `--disable-image-metadata`. The last switch, `--max-vram`, is `-3` unless part of the card is in use (step 6: see "The engine does not see what other programs hold" in the short map).
- **Every clip is checked before it is handed on** (`VideoClips.Problem(webm, request)` in `VideoServer.MakeWithAsync`, again in `Clip.Problems()`): `WebmInfo.Read(bytes, out problem)` walks the file by structure and lets through only the parts in its `Known` table (header "webm", seek index, the facts as numbers plus the two program names, **one `V_VP8` video track**, cues, frames one a block). Tags, an attached file, chapters, a title, a date, a track name, sound, a second track, bytes after the end, padding that is not empty, a program name with a space or over 40 characters, and **any part not in the table** are refused with a reason. The engine's own file passes as it is; its muxer gives the track a random number, so the same seed gives the same frames in a file that differs in 7 bytes. A new engine version that writes another part needs that part added to `Known` after looking at it (`VideoSmokeTests.Tree` prints a file's parts).
- **`SdApi`** has `VideoBody`, `StartVideoAsync`, `VideoJobAsync`, `MakeVideoAsync`, `ParseVideoJob`. The body has no `batch_count`, `embed_image_metadata`, scheduler or tiling; the first frame is `init_image` as plain base64. `generation_info` (it repeats the prompt) is never read: `SdVideo` and `SdVideoJob` have no place for it. A clip is polled once a second (`VideoPollInterval`), so a stage shorter than that (`vae_encode`, the fast decoder's `vae_decode`) is not always reported: never wait for one. Preview is `"tae"` (a full-size PNG, 0.5 MB at 832 × 480), repeated by the engine on every poll and passed on once.
- **Log:** `VideoServer.Logged` only ("video engine: …"), through its own `PictureLogFilter`, told **the sentence** before the request leaves (not the fixed negative prompt, which is in the source and would only hold status lines back). `Output` is never logged.
- **Kept clips** are the `Clips` table: `Clip`, `ClipOwners` (`Video` with id 0 for the Video section; `Message`, `Character`, `Persona` have triggers `Clips_*_ad` like pictures), `IClipStore` / `SqliteClipStore`. `AddAsync` is the only way a clip reaches the disk and takes only what `Clip.Problems()` passes (the WebM check with the clip's own size and frame count, a still by `PicturePreview`'s rules, the first frame as the request checks it, the model's four files as paths inside their own folders: `VideoFiles`, never a full path). **`Still`, `StartFrame`, `Video` are the last columns in that order** (a test pins the list); lists (`PageAsync`, `FactsAsync`) read the still and never the other two. A later column is not added with `AddColumn`: rebuild the table and drop and recreate the three triggers, as for `Pictures`. `Clip.Of(ownerKind, ownerId, files, request, result, still)`, `ToRequest()`, `ModelIn(videoRoot)`.
- **Folders:** `AppSettings.VideoFolder()` = `<models>\video`; `VideoFolders.ModelFor(root, VideoFiles.Wan22)` gives the four paths (`diffusion_models`, `text_encoders`, `vae`; both decoders are in `vae`). Recognising, downloading and deleting them is the Models section (see "Video in the Models section (M20 step 3)").
- **Tests:** `VideoTests.cs` (`TestWebm.Make(…)` writes a WebM that is whole by structure, with options for each thing a clip must not have; `FakeVideoSd` is a pretend sd-server for the video route; `FakeVideoEngine` for anything that asks for clips), `ClipStoreTests.cs` (store, column order, upgrade and back, removed data, triggers, lock, backup and restore, portable), `VideoSmokeTests.cs` (the real engine: `DOGAI_SD_SERVER` and `DOGAI_TEST_VIDEO_DIR` = a video models folder; with `DOGAI_TEST_MODEL` and `DOGAI_LLAMA_SERVER` also a real chat model beside a full Quick clip; `DOGAI_TEST_VIDEO_OUT` = a folder to save the clips for a look, off otherwise). Run its three tests one at a time: about 1.5, 3 and 3.5 minutes.
- **Measured here** (RTX 4090, the installed CUDA engine): a short clip (33 frames, 832 × 480, 8 steps) 13 to 15 s; a full Quick clip 149 s with the chat model set aside first (estimate 146 s cold); the model's own decoder on a short clip 22 s; cancel 2.2 s; the card back at 1.4 GB after every clip.

## How video works: the short map (M20, finished in step 6)

- Order of reading: the trial (step 1) → Core, storage and engine (step 2) → Models (step 3) → Make (step 4) → Kept videos and Animate… (step 5). The five sections above keep each step's rules and ids; this is what holds across them.
- **Three places hold things, and only one of them is the disk.** `VideoSession` (memory only: the sentence, the first frame, at most four tries, a clip in progress); `VideoChoices` (document `video`: quality, shape, seed); the `Clips` table (kept clips: the video, its still, its first frame, its sentence). A sentence or a first frame reaches the disk only inside a kept row. A picture from elsewhere arrives only through `AnimateButton` → `VideoSession.Hold`; a file only through the page (`attach.js` `openFrame` → `VideoFrames.Cut` → `cutFrame`).
- **One path for every clip:** what is typed and chosen → `VideoRequest.For` → `VideoSession.MakeAsync` → `IVideoEngine` (`CardCoordinator`) → `VideoServer` → `SdApi.MakeVideoAsync` (`POST vid_gen`) → `VideoClips.Problem` → a `VideoTry` in memory → Keep (`VideoTry.ToKeep` → `IClipStore.AddAsync`). The request body holds exactly: `prompt`, `negative_prompt`, `width`, `height`, `seed`, `video_frames`, `fps`, `sample_params` (`sample_method`, `sample_steps`, `guidance.txt_cfg`, `flow_shift`), `output_format`, `output_compression`, `preview`, `preview_interval`, and `init_image` (plain base64) when there is a first frame. Recorded in step 6: no address, path or `data:` in any request; Make one like this sends the kept clip's request byte for byte; Images' own request has no input picture.
- **The engine does not see what other programs hold on the card** (found in step 6). Its own measure reported 23.0 GB free while another program held 6.8 GB; with `--max-vram -3` it then put the whole model on the card (21.7 GB of its own), filled the card to 23.9 GB, borrowed 2.8 GB of Windows' shared memory, and a clip of 58 seconds took 222. So DOG.ai tells it: `CardCoordinator.MakeAsync` passes the free memory it measured after clearing the card to `IVideoEngine.MakeAsync(model, request, cardFreeBytes, progress, ct)` (a default on the interface; `VideoServer` implements it), and `VideoMemory.EnginePlan(free)` is the program's `--max-vram`: `-3` when the card could not be measured or has `WholeModelFree` (22 GB) free, as in every clip measured in steps 2 to 5; else a plan in GiB with one decimal, what is free less `PlanReserve` (3 GB), never over the decoder's cap: `PlanCap` (10 GB) for the fast decoder (Quick), `PlanCapOwnDecoder` (13 GB) for the model's own (Better); `EnginePlan(free, decoder)`. **The cap is what matters, and the two decoders want opposite things.** For the fast decoder: with a plan of 11 GB or less the engine keeps the model itself (9.5 GB) in RAM and brings it to the card piece by piece; it then takes the plan and about 2.8 GB (8.6 GB at a plan of 5.8, 13.8 GB at 11) and turns the clip into frames in a second or two. With 12.5 GB or more it keeps the model on the card and takes 17 GB while the clip is turned into frames, whatever it was told: beside a 6.8 GB program that step took 13 seconds in one run and had not ended after 2½ minutes in another (in the app, plan 13.1). Over 15.3 GB (the whole model) it takes 21.7 GB. The model's own decoder works in pieces and needs the model kept on the card: with a plan of 12.5 to 13.1 GB a Better clip took the engine 13.6 GB and decoded in its usual 3¼ minutes; with 10 GB its decoding had not ended after nine minutes and free RAM fell to 1.8 GB. In the app beside a 6.8 GB program, with the final rule: Quick 2 min 23 s (estimate 2 min 26 s), Better 7 min 33 s (7 min 19 s). **A crowded card also gets no previews** (`request with { Preview = false }`): with a plan of 12.9 each full-size preview took most of a minute (4 min 26 s for a Quick clip, estimate 2 min 26 s). `CardCoordinator.IsVideoCrowded` is true meanwhile; the page says so through `VideoPanels.Doing(progress, crowded)` and `WhileMaking(decoder, crowded)` (wording `VideoPanels.Crowded`). Change the numbers only after measuring with another program on the card, **in the app** as well as with the engine alone (the app's own window takes a little of the card, and that was the difference between 13 seconds and a hang).
- **A card slow to give memory back is looked at again:** `ClearForVideoAsync` reads the card up to four more times (`PollInterval` apart) while it looks crowded, also when DOG.ai moved nothing: a clip straight after a clip can find the last video program's memory not yet given back.
- **A try is changed by its number** (`VideoSession.Change`, behind `Kept` and `WithStill`), never by reference: Keep can be pressed while the clip's still is being made, and then holds the record from before the still arrived (the review: the clip stayed unmarked and a second Keep wrote it twice). The page makes a clip's still once (`VideoMake._stills`: a clip arriving, the player and Keep all ask).
- **The player is let go before its element leaves, and nothing refills it meanwhile:** `VideoMake.ReleasePlayerAsync` clears `_playing` only after the page has let go; `KeptVideos` has `_changing` (set while the view opens another clip, closes, or hands a clip to Make), and `OnAfterRenderAsync` plays nothing while it is set. The page renders every second while a clip is made, so a render does come in between. A clip paused for a Draw that was cancelled or refused plays on (`video.js` `resume`).
- **A clip's job answers are read in place:** the engine repeats its newest preview (up to 1.9 MB of text) in every answer, once a second for minutes. Read as a string and taken apart into objects that was about 10 MB of short-lived copies a poll, and DOG.ai's own memory went from 0.2 to 1.9 GB over ten clips. `SdApi.VideoJobAsync` reads the answer into a borrowed buffer (`ArrayPool`, wiped when given back: it holds the clip and, in `generation_info`, the sentence) and `ParseVideoJob(ReadOnlySpan<byte>, shown)` walks it with `Utf8JsonReader`: a preview with the same step and base64 length as the one shown stays text, `generation_info` and anything unknown is skipped unread, an answer cut short never throws. A scratch console program that starts the real engine with a chosen `--max-vram` and samples the card, the engine's own `Dedicated Usage` and `Shared Usage` and free RAM per stage was how the numbers above were found; "Shared Usage" also counts model parts kept in RAM, so it is no sign of overflow by itself: the time is.
- **Walkthroughs (step 6):** helpers put on `window` (`W.nav`, `W.draw`, `W.clip`, `W.keep`, `W.say`, `W.reply`…) and step lists built in PowerShell made nine app runs affordable; each run is its own script started with `Start-Process pwsh -File`, writing a log and a `.done` file. A PowerShell `[string]` parameter turns `$null` into `""`: test with `IsNullOrEmpty`. `@{ reconnect = 1 }` after `@{ adopt = 40 }` connects to the page of a restarted DOG.ai whose data is not locked (a restore's restart; a locked one reconnects through its `lock` step). **A real window is never narrower than 886 page px** (`winsize = '1072x1340'`), so `winsize` cannot show a 700 px page: use `-Width 700` for that, and `winsize` for the widths between (where Playhouse's bar broke). A kept clip is seen to play by `#kept-clip-player`'s `currentTime` rising above 0. `[data-mid]` counts chat messages. The backup buttons have no ids: find them by their words ("Back up now…", "Restore from a backup…", "Restart and restore"); the restore dialog's title is "Choose a DOG.ai backup".

## How pictures share the graphics card (M9 step 3)

- `IImageEngine` from the app's services is `CardCoordinator` (Core/Images) wrapped around `ImageServer` (Engine/Images). Draw only through it; only the engine's own screens (install, update) use `ImageServer`.
- Per picture it estimates the need (`PictureMemory`), measures the card (`ICardMeter`, implemented by `CardMeter`), and either keeps both models or sets the chat model aside: `EngineManager.RestAsync` gives `EngineState.Resting`, where the program is gone but model, context size and settings are remembered. `IsReady` is true while resting (chat pages keep working) and the next request loads the model again (`BeginUseAsync`); `IsLoaded` is true only when it is in memory. Use `IsLoaded` for passive things that must not bring it back (token counts while typing).
- Setting aside is not the owner's unload: never route it through `ModelLauncher.UnloadByUserAsync`, and never load a chat model from the coordinator.
- A load nobody asked for yet is not waited for. `ModelLauncher.LoadDefaultIfIdleAsync` loads with `automatic: true`; `EngineManager.SetAsideLoadAsync` (`IChatModelSlot`) stops only such a load and leaves the model `Resting`. The coordinator calls it before waiting for its turn, so a picture right after opening a page does not wait half a minute for a model it would set aside. Never pass `automatic: true` for the owner's load, a benchmark, or a wake for a request.
- A model somebody asked for never waits behind a page's own load: `ModelLauncher.LoadAsync` (not automatic) takes its turn through `TakeTurnAheadOfPageLoadsAsync`, which stops such a load (`EngineManager.DropAutomaticLoadAsync`: the model is forgotten, not set aside) and looks again until the turn is its own, because the page's load holds the turn a moment before the engine says "Loading". An automatic load that waited for its turn does nothing unless the engine is still `Idle`. Load a model for the owner only through `ModelLauncher.LoadAsync`.
- One thing at a time changes the card. Every chat model load takes a turn first and keeps it until the load ends: `ModelLauncher.LoadAsync` and `ModelBenchmark` do (`EngineManager.TakeCardTurnAsync`); raw `EngineManager.LoadAsync` does not, so do not call it from new code without a turn. A picture waits for a request in progress, so never draw from inside a streaming request: finish the chat model's job first.
- A waiting picture reports the stages `CardCoordinator.Waiting` and `MakingRoom`. The coordinator's `Noted` lines go to the log ("Graphics card: …") and never contain a prompt.
- The picture model is let go after `ImageServer.IdleStop` (2 minutes), or at once when the chat model needs the room. Drawing counts as busy for the idle lock through `IImageEngine.IsBusy` in `AppLock`.

## How image models work (M9 step 4)

- Folder: `AppSettings.ImageFolder()` = `<models>\image` with `checkpoints`, `loras`, `vae`, `upscalers` (`ImageFolders`, Core), created only when needed (`ImageLibrary.Ensure`, Engine: on Open folder, a download, a picture). The names match sd-server's own layout.
- Recognition: `SafetensorsHeader` and `ImageFileRecognizer` (Core, pure) read tensor names and a few metadata fields; `ImageLibrary` (Engine) opens files read-only, reads only the header and remembers results by size and date. `.ckpt`, `.pt`, `.pth`, `.bin` are never opened (refused). Family is guessed from whole words in names (`Words`), never substrings; metadata is untrusted and never shown wholesale (it can hold the maker's own file paths).
- Settings: `ImageModelCatalog` (Core) is one JSON document (key `image-models`) in the settings store. Files are named by their path inside their own folder, never a full path, so `PortableMove` needs nothing new. A card is saved only when the owner changes it; untouched ones follow `CheckpointSettings.ForFamily`. `ImagePrompt.Compose` turns a card plus LoRAs into an `ImageRequest`; `ImageFolders.ModelFor` gives the `ImageModel`.
- UI: `Components/Models/ImagesTab.razor` (+ `CheckpointCard`) is On this PC › Pictures; the recommended downloads are `PictureDownloads` (Get models › Pictures); the picture engine's install and update (`PictureEngineBox`) live only in Models › Engines (see "How the Models section is laid out"). Image downloads carry `ImageDownloads.UseCase` and never become chat-model records.

## How kept pictures work (M9 step 5)

- A kept picture is a row in the `Pictures` table: `Picture` and `IPictureStore` (Core/Images), `SqlitePictureStore` (Data). `IPictureStore.AddAsync` is the only way a picture reaches the disk: pictures that are tried and not kept stay in memory. Never write a picture, thumbnail or preview to a file or cache; show them from memory (`data:` address).
- Draw anything that may be kept with `request.ForKeeping()` (WebP at `PictureFormat.Quality`, 90, chosen by eye; the engine encodes it). `Picture.Of(...)` makes the row from a request and its result; `ToRequest()` and `ModelIn(imageRoot)` draw it again (same seed and settings give the same bytes).
- The owner is `OwnerKind` + `OwnerId` (`PictureOwners`: character, persona, message, test), with no foreign key. Triggers in the `Pictures` migration delete a message's, character's or persona's pictures with it; a new kind with its own table needs a trigger in a new migration.
- Files are named by their path inside their own folder; the store refuses full paths and anything that is not WebP (`WebpInfo`). Never add a column holding a full path, so `PortableMove` keeps needing nothing.
- Log: only `ImageServer.Logged` is written to the log (`picture engine: …`). It passes through `PictureLogFilter` (Core): status lines only, and none sharing a word with a prompt sent in the last ten minutes. `ImageServer.Output` is everything the engine prints and must never be logged. Anything new that sends text to the picture engine must tell the filter first (`Sending`).
- For checks: `$env:DOGAI_TEST_PICTURE_WORDS` adds its words to the test picture's prompt and shows `#keep-picture`, `#keep-note` and `#kept-pictures` (rows `[data-picture]` with `[data-act=again]` and `[data-act=remove]`) under the test picture.

## How picture prompts work (M9 step 6)

- **Looks** (`Looks`, Core/Images): a person's appearance words plus an optional character LoRA and strength. A character's are in the card (`extensions.dogai.looks` in `Character.ExtraJson`, through `CharacterCard.LooksJson` / `WithLooks`); a persona's are `Persona.LooksJson`. Read with `Looks.Of`, write with `SaveTo`; every read is cleaned (`Clean`: one line, 1,000 characters, a LoRA only as a `.safetensors` path inside the loras folder), because cards are untrusted. **An imported card's Looks are checked once, at import** (`Looks.CheckImported` in `CharacterList.ImportAsync`): pieces that are, or contain, a tag on the left-out list go (`TagList.LeavesOut`, the same cases `Resolve` drops for that reason, plus such a tag written as one word), unless the full tag list is on; the note (`#import-note`, `Looks.ImportNote`) says how many, never which. Any new way a card comes in from outside must call it too; never call it on what the owner is editing. Looks are never sent to the chat model in chats. UI: `Components/Images/LooksBox.razor` (ids `#looks-tags`, `#looks-draft`, `#looks-note`, `#looks-lora`, `#looks-strength`). It has two drafts: **Draft from the description** (`DraftLooksAsync`) and **Draft from the portrait** (`#looks-from-portrait`, `DraftLooksFromPictureAsync`, M19 step 2: the model looks at the editor's picture; see "Looks from the portrait (M19 step 2)"). Both replace the words unsaved, keep the LoRA, and go through the tag check.
- **The chat model never writes a prompt.** `PictureWriter` (Core/Images; a DOG.ai model job: schema, `Thinking = false`, answer checked) fills a form, `PictureScene`: one sentence on the moment, then per person kind, looks, clothing, expression and pose, then place, light, one framing (`Sizes`) and one view (`Views`). `PortraitAsync` plans one person from a card; `SceneAsync` plans a passage (pass each cast member's `CastEntry.About`); `DraftLooksAsync` drafts a Looks box.
- **Code builds the prompt:** `PicturePrompt.Assemble(scene, PictureOrder, tags)` gives a `PlannedPicture` (request, subject, `TagNotes`). Order: quality words, LoRA triggers, count tags ("1girl, 1boy", "solo", "no humans"), each person's looks then clothing, expression, pose, then place, light, framing. A person with Looks gets them exactly as typed and the model's looks for them are ignored; a count tag ("1girl") in Looks says what they are. Sentence-style checkpoints get the same slots as phrases with no tag check. It ends in `ImagePrompt.Compose(...).At(quality, shape)`.
- **Tag check:** `TagList.Bundled` is `Images/Tags/tag-list.txt` (embedded; Danbooru and e621 general tags and e621 species, 100+ posts; source and licence in `Tags/README.md`; rebuilt by `tools/make-taglist.ps1`, never downloaded by the app). `Resolve` keeps a real tag, corrects a near miss, else drops; it must prefer dropping to a doubtful correction (guard words, no whole-short-word changes, no sentences). No artist, character or series tags are in the list on purpose. The owner's own Looks are never checked. When a wrong correction turns up, add a test and tighten the rule (or `NotASpelling`); do not special-case the prompt.
- **Left-out tags (owner's decision, 2026-11-14):** some tags are left out of the bundled list on purpose, and the repo does not hold them as words. They are SHA-256 fingerprints in `Images/Tags/excluded-tags.txt` (`TagFingerprints`: hash of `TagList.Normalise(tag)`); `make-taglist.ps1` drops any tag or spelling listed, and `Resolve` drops a written tag that is one in any spelling (`IsLeftOut`, before any correction) or that contains one outside a longer kept tag (`ContainsLeftOut`, after the plural/singular). Add more only with `tools/tag-fingerprints.ps1` from a word list outside the repo. Never write such a word into a file in the repo, a commit message, a test (use made-up tags) or the log; `DOGAI_TEST_TAG_CSV` (the pinned source file) turns on the checks against the real tags, which print counts and fingerprints only.
- **Tag files:** `TagCsv` (Core) is the one reader for tagcomplete CSVs, used by the build script (it builds DogAI.Core and calls `BuildBundledList`) and by the app; change the rules only there. Strict: 64 MB, UTF-8, four fields a line, or the whole file is refused (`TagFileException`, in words for the owner).
- **Extra tags (the opt-in full list):** `ExtraTags` (Engine/Images, singleton) keeps it as `<image>\tags\full-tag-list.csv` (a fixed name; the file is the switch, nothing is saved), loads it at start (`StartModelServicesAsync`) and after its download (use case `image-tags`), and puts `TagList.Bundled.With(rows)` into `TagList.Current`. Picture code uses `TagList.Current` (`Bundled` is the list DOG.ai ships). UI: `Components/Images/ExtraTagsBox.razor` in Models › On this PC › Pictures › Tags (`models/pictures/tags`; `#extra-tags`, `#extra-tags-state`, `#extra-tags-add`, `#extra-tags-download`, `#extra-tags-choose`, `#extra-tags-cancel`, `#extra-tags-remove`, `#extra-tags-error`); Settings → Pictures shows `#rating-tags-note` while it is off. Tests that change `TagList.Current` go in the `CurrentTagList` collection. Its download comes from GitHub: `FileTransfer` sends the Hugging Face token to Hugging Face hosts only; keep it that way for any new non-HF download.
- **Quality and shape:** `PictureLevels` (`PictureQuality` Draft / Standard / Fine, `PictureShape` Tall / Square / Wide). `request.At(quality, shape)` changes only steps, size and the hires fix, so a kept seed redraws at another level. The numbers (Draft 70% of steps with a floor of 16; Fine ×1.5 Lanczos, strength 0.3) and the Illustrious defaults (Euler, 28 steps, guidance 5.5) were chosen by looking at pictures; do not change them without looking again. Euler matters: with Euler a every step count is a different picture, so a Draft would not preview Standard.
- **Style LoRAs** of a checkpoint are `ImageModelCatalog.StyleLorasFor` / `SetStyleLorasAsync`, kept beside the settings cards, not in them (ticking one must not turn a card into "your settings").
- The rating is added by code: `PictureOrder.Rating` → `ImagePrompt.Compose(..., rating)` → `PictureRatings.Apply` (see "How portraits work").
- For checks: the Test picture (On this PC › Pictures) has `#test-quality` and `#test-shape` beside `#test-picture`; style LoRA boxes are `[data-style-lora]` inside a checkpoint's open settings. `PictureWriterSmokeTests` runs the jobs with a real model when `$env:DOGAI_TEST_MODEL` is set and prints the prompts (`--logger "console;verbosity=detailed"`); it draws nothing.
## How portraits work (M9 step 7)

- **Picture maker** (`Components/Images/PictureMaker.razor`, a modal): Draw (the chat model plans through the `Plan` parameter, then the picture is drawn), Try again (same plan, new seed: no model job, so a set-aside chat model stays aside), Edit and redraw (prompt, quality, shape or LoRAs changed, seed kept), Cancel, Use this picture. It is reusable: the page passes `Plan`, `People` (name + `Looks`), `OwnerKind`/`OwnerId`, `DefaultShape`, `ChatMode`. Ids for checks: `#maker-draw` (says "New idea" after the first try), `#maker-again`, `#maker-edit`, `#maker-edit-prompt`/`-quality`/`-shape`, `.maker-lora[data-lora]`, `#maker-redraw`, `#maker-use`, `#maker-cancel`, `#maker-status`, `#maker-error`, `#maker-meta`, `#maker-details`, `[data-try=N]`, `#maker-review` (`#maker-moment`, `#maker-notes`, `#maker-prompt`, `#maker-review-draw`).
- **Tries** are `PictureTry` records in `PictureTries` (Core/Images), in memory only, at most 12 (a kept one is never dropped). Each keeps `Base`: the request at the checkpoint's own step count. Always apply a level to `Base` (`PictureTries.Levelled`), never to an already-levelled request: `At` reads the checkpoint's steps. A kept picture comes back with `Adopt` (its quality is told from its steps and hires fix, `BaseOf`; its own checkpoint, VAE and prediction are kept).
- **Keeping:** Use hands back `PictureMaker.Used` (the try and a PNG). The PNG is made in the page (`wwwroot/js/pictures.js`, canvas, in memory), so Windows' WebP support is not needed; the editor gives it to `PreparePictureAsync` and the existing cropper. The `Pictures` row is written only when the character or persona is **saved** (`ToKeep` → `AddAsync` after the save returns the id), so a cancelled edit leaves nothing. An owner keeps **one** row: the portrait in use, through `Portraits.KeepAsync` (adds the new row before deleting the others); picking a file or Remove deletes it on save. Reopening the maker shows that row ("The picture in use") for Edit and redraw.
- **Chat model for a job:** `ModelLauncher.EnsureReadyAsync(settings, mode, ct)` waits for a load already under way (opening Characters → New starts loading the default), else loads the mode's default. Use it for any new model job started from a button, not `LoadDefaultIfIdleAsync` alone (that returns at once while a load is under way).
- **Settings → Pictures** (`Components/Images/PictureSettings.razor`): the checkpoint is `ImageModelCatalog.Chosen` (the same as the Pictures default in On this PC › Chat models, and "Draw with" in the test picture); default quality, "Show me the prompt before drawing" and the rating are `PicturePreferences` in the `image-models` document (`Catalog.Preferences`, `SetPreferencesAsync`).
- **Rating:** `PictureRating` (four levels). The words per level are `CheckpointSettings.Ratings` (`RatingWords`; null = the family's, `RatingsOrDefault()`; cards saved before step 7 have none), edited on the checkpoint card. `PictureRatings.Apply`: the chosen level's words after the quality words; the words of every level above into the negative prompt, without repeats and never a word the chosen level uses itself; nothing else. Rating words never go through the tag check. The planning jobs take the rating (`PortraitAsync`/`SceneAsync`/`SceneInstruction`, `PictureRatings.ForPlanner`).
- Never log a moment sentence or a prompt from the maker.
- **Try again takes the rating chosen now** (`PictureRatings.Reapply`: swaps the rating words right after the quality words and rebuilds the negative prompt from the card). Edit and redraw does not: its prompt is the owner's to change.
- The maker says what it waits for (`StatusText`): planning while the chat model is not loaded (it was set aside and comes back first), and drawing while a chat model is `Loading` (loading the picture model takes the card turn and reports no progress, so the status would otherwise sit at "Starting…").

## How story illustrations work (M9 step 8)

- A passage shows at most one kept picture above it. It is a `Pictures` row owned by the passage's message (`PictureOwners.Message`, id = message id); `StoryTurn.Picture` (JSON `picture`, in `ChatMessage.ExtraJson`) records which row. A passage keeps **one** row. Core: `Illustrations` (Core/Stories): `People` (cards in cast order with `Looks.Of(card)` and `PictureWriter.About(card)`, then Cast-box names with no Looks and the rest of their line as `About`), `PlanAsync` (`SceneAsync`, at most `MaxPeople` = 2, premise and world as background), `KeepAsync` (add the row, point the passage at it, then delete older rows; a gone passage leaves nothing), `RemoveAsync`, `LoadAsync` (for exports), `Shown`.
- Change a passage's story details only by reading it fresh (`StoryTurn.Of` on the current message) and writing all of them back (`SetMessageExtraAsync`): `ChatService.SetPassagePictureAsync` does; `ChoicesAsync` re-reads before saving so a picture kept meanwhile is not lost. Rewrite makes a sibling passage with no picture; Edit and Continue keep it.
- UI: `StoryThread.razor` (`.illustration[data-picture]` button above `.passage`, `button.illustrate` in its actions: "Illustrate" or "Redraw picture"; large view `.picture-view` with `#picture-large`, `#picture-redraw`, `#picture-remove` → `#picture-remove-yes`, `#picture-meta`). Pictures are read once per id and kept as data: strings in memory (never a file); the thread re-renders on every streamed token, so do not re-encode per render.
- Exports: `StoryExport.ToHtml`/`ToEpub` take pictures by id (`ExportPicture`): HTML embeds WebP as `data:`; EPUB gets JPEG at 92 made in the page (`pictures.js` `toJpeg`), as `OEBPS/images/picture-N.jpg` manifest items, the `<figure>` written outside the markdown so the plain-paragraph fallback keeps it. Markdown has no pictures.
- Deleting a passage's message or its story deletes its pictures (the `Pictures_message_ad` trigger). There is no per-passage delete in the UI.

## How chat pictures work (after M9)

- A reply in a character chat or group chat can show one kept picture, stored exactly as a story passage's: a `Pictures` row owned by the message, pointed at by `picture` in `ChatMessage.ExtraJson` (read with `StoryTurn.Of`, shown with `Illustrations.Shown`, kept and removed with `Illustrations.KeepAsync` / `RemoveAsync`). No table or migration of its own.
- `ChatPictures` (Core/Chat) says who may be in it (`People`: the characters in order, then the persona, each with their own Looks; a persona named like a character is left out) and what the planner reads (`PlanAsync`: the reply as "Name: text", and `Background`, up to six earlier messages, newest kept, under the planner's 1,500-character cut). At most two people.
- UI: `Components/Images/MessagePictures.razor` is shared by `StoryThread` and `ChatThread`: it reads the branch's pictures once into memory (one load at a time, as before), and owns the large view and the picture maker. A thread draws the small picture and the button itself through `Src`, `View` and `Illustrate`. It raises `OnLoaded` only when the set of pictures changed; raising it on every load would loop, because the thread's render sets its parameters again.

With nobody, the planner gets no names and no setting, only the reply and the messages before it (`NameOf` gives a General reply the model's name, else "Assistant"), and the maker's first line leaves out Looks (`ChatPictures.MakerIntro`). ## How pictures work: the short map (M9, finished in step 9)

- Order of reading: the engine (`ImageServer`, step 2) → sharing the card (`CardCoordinator`, step 3) → image models and settings (step 4) → kept pictures (step 5) → prompts (step 6) → the picture maker and portraits (step 7) → story illustrations (step 8). The sections above have the rules for each.
- **Starting an engine program:** `EngineEnvironment.StartQuietly(process)`, not `process.Start()`. It keeps Windows from showing its "…dll was not found" box, behind which the program would sit alive and unanswering for the whole start timeout. The program then ends at once with an exit code; `EngineFailure.StartProblem(exitCode)` puts the codes Windows gives for "could not start it" into words and `ImageServer.StartFailure` makes the picture engine's message ("…Install it again in Models › Engines"). Only the picture engine uses it so far; llama-server and the document search model still start with `process.Start()`.
- **A damaged engine copy** is repaired with **Install again** (`#picture-engine-again`, beside "Up to date" in `PictureEngineBox`); it runs the same `InstallAsync`.
- **One place each:** progress wording is `PictureWords.Of(progress)` (UI); a model's paths are `ImageFolders.ModelFor` (also for a kept picture, through `Picture.ModelIn`); a try's `data:` address is `PictureTry.Src` (made once per picture; do not build it again per render).
- **Extra tags follow the image folder in use:** call `ExtraTags.FollowAsync(imageRoot)` wherever tags are about to be checked (the picture maker and the Looks box do), so a changed models folder is noticed without a restart.
- **The maker's body is a grid that scrolls.** A row that scrolls sideways (`.maker-tries`) needs a `min-height`, or the grid squeezes it to nothing when the maker is taller than the window. Check any new row in the maker with a Tall picture at the walkthrough's window size.
- **Real-engine tests ask without thinking** (`Thinking = false`): a model that thinks first can spend a small token budget on it and answer nothing.
- **`StoryThread.LoadPicturesAsync` runs one load at a time**; a render that arrives meanwhile asks for one more look afterwards. Keep it that way: the thread's parameters are set on every streamed token.
- **Leak checks** (step 5 and step 9): draw with a marker word per picture (`DOGAI_TEST_PICTURE_WORDS` for test pictures; a word added in **Edit and redraw** for the maker), save each picture's `data:` address with a walkthrough step `@{ eval = "..."; save = '<file>' }`, then search the data folder, logs, WebView2 folder, models folder, engine folder and TEMP for the words (any case, UTF-8 and UTF-16) and for byte and base64 pieces of every picture. A plain data folder must hold only what was kept; a locked one nothing.

## How removed data leaves the disk

- Deleted rows must not stay readable in a plain database. Three things do it: the SQLite build is compiled with secure delete (deleted content is zeroed; `RemovedDataTests` pins it, so check that test after any SQLite package change); the search index has FTS5's own `secure-delete` on (`SearchWipe` migration); and `DatabaseTidy` (Data) empties the `-wal` file shortly after any delete and once after each start.
- `DeleteWatcher` (an EF command interceptor added in `AddDogData`) tells `DatabaseTidy` about every command whose text contains DELETE. So delete through EF (`ExecuteDeleteAsync`, as every store does); a delete on a hand-made `SqliteConnection` must call `DatabaseTidy.Deleted()` itself.
- A new FTS5 table needs `INSERT INTO <table>(<table>, rank) VALUES('secure-delete', 1)` in its migration.
- Tests that search a data folder's bytes wait with `DatabaseTidy.SettledAsync()` and must tolerate `-wal`/`-shm` files vanishing (`SqliteConnection.ClearAllPools()` in another test class closes everyone's pooled connections).

## How locked data works (M8)

- **SQLite build:** `SQLite3MC.PCLRaw.bundle` (SQLite3 Multiple Ciphers, ChaCha20-Poly1305) with `Microsoft.EntityFrameworkCore.Sqlite.Core`; never add the plain `Microsoft.EntityFrameworkCore.Sqlite` or `Microsoft.Data.Sqlite` package (it would bring a second, plain SQLite). A plain database works on it exactly as before.
- **Every connection goes through `DatabaseLock.ConnectionString(file, key)`** (Data). The key is 32 bytes, given as `raw:<hex>` in `Password`; `null` means a plain database. Never write a connection string by hand. The running app's key is the `DatabaseKey` singleton (Core/Privacy; `Bytes` is null when the lock is off), registered by `App.BuildServices`; `AddDogData` and `SqliteBackupService` read it. Static helpers (`DatabaseBackup`, `PortableMove`) take the key as an optional last argument.
- **Core** (`DogAI.Core/Privacy`): `LockFile` (`lock.json` beside the database: the database key wrapped by password and by recovery key with PBKDF2-SHA256 600,000 rounds + AES-GCM, and per PC by a Windows Hello signature through HKDF; a `Check` value lets code confirm it holds the right key before re-wrapping; `WithoutHello()` for backups; `Pending`, `Skin`, `Theme`), `RecoveryKey`, `UnlockThrottle` (count kept in `unlock-tries.json`), `Unlocker` (what the lock screen does), `IHelloSigner` (implemented by `WindowsHello` in App; tests use `PrivacyTests.FakeHello`). Tests pass a low round count to `LockFile.Create`.
- **Encrypt and decrypt** (`DatabaseLock.Encrypt` / `Decrypt`): a `VACUUM INTO` copy under the new key, compared with the original (integrity check, schema, row count of every table), swapped in, WAL mode put back. Not `PRAGMA rekey` (it refuses WAL databases). They run **only at start**, from `DataLock.Settle`, because nothing else may have the database open. `DataLock.Look` tells the state from the files alone: `Off`, `Locked`, `TurningOn` (lock file present, database still plain: it is encrypted when the password is entered at the lock screen), `TurningOff` (`LockFile.Pending`). So turning the lock on from a future Settings screen means: write `lock.json`, restart. `DatabaseLock.Recover` tidies a conversion that was cut short.
- **Start-up order** in `App.OnStartup`: `DatabaseBackup.ApplyPending` (moves files only, needs no key) → `PortableMove.MovedFrom` → `Unlock` (`LockWindow`, a plain WPF window; nothing else exists yet: no services, tray, global key or model) → `DatabaseBackup.FinishRestore` and `PortableMove.Apply` with the key → `BuildServices`. Anything new that opens the database at start goes after the unlock. `Application.MainWindow` is set by hand because the lock screen is the first window WPF sees.
- **Backups:** a locked database gives an encrypted `dogai.db` plus `lock.json` (no Hello entries) and a manifest with `Locked = true` and no counts (format 2; plain backups stay format 1). `StageAsync` takes this DOG.ai's key and the backup's password or recovery key (`BackupLockedException` when missing or wrong). What is staged for a locked DOG.ai is always under its own key; a locked backup staged for a plain DOG.ai brings its lock file along.
- **Settings → Privacy** is `Components/Library/PrivacySettings.razor` over `PrivacyLock` (Core/Privacy). Every change re-reads `lock.json` first (the lock screen may have changed it). Turning on writes `lock.json` only after the recovery-key check (`RecoveryCheck`); a new recovery key is shown and checked before `UseRecoveryKeyAsync`; turning off sets `Pending` and restarts. Password rules: `LockPassword`. The lock screen's look and the tray setting are copied into `lock.json` (`LockLook`) by `AppLock`.
- **Lock screen look:** `LockWindow` + `LockStyles.xaml` + `LockPalette` (App/LockLooks.cs). Its colours are copied from the tokens in `app.css`; change both together.
- **Locking:** `AppLock` (App, behind `IAppLock`): Lock now, the idle lock (`IdleLock` in Core: PC-wide idle from `GetLastInputInfo`, never earlier than the unlock, postponed while busy for at most one more period; `DOGAI_IDLE_LOCK_SECONDS` shortens it for tests), and Ctrl+L (`LockKey.razor` with `chat.js` `watchLockKey` in the page, and `MainWindow.PreviewKeyDown` for when the page has no focus). The recovery key prints alone through `chat.js` `printOnly` and the `print-one` rules in `app.css`. Locking is `WpfDesktopShell.RestartProcess(hidden)`; it sets `WpfDesktopShell.Exiting` so close-to-tray never keeps the old process. `--hidden` starts the lock screen in the tray. While locked, `App.LockedTray` shows a tray icon with Quit only.
- llama-server never inherits `LLAMA_ARG_*` / `LLAMA_LOG_*` settings (`EngineEnvironment.Clean`); a new engine process must call it too.
- Exports through `IDesktopShell.SaveFileAsync` show a one-time note while locked (`AppSettings.PlainExportNoted`).
- Never log a password, recovery key, key or connection string.
- Walkthrough: `tools/walkthrough.ps1 -LockSteps @(@{ set = @{ Password = '...' } }, @{ click = 'Unlock' }) -Steps ...` drives the lock screen by its controls' automation ids (see the script's header); on a PC with Windows Hello the first unlock of a data folder then asks "Use Windows Hello on this PC?", so add `@{ wait = 3000 }, @{ click = 'NotNow' }, @{ gone = 60 }`. A data folder locked from before its first start: write `LockFile.Create(password).File.ToJson()` to `lock.json` in the empty folder (load `DogAI.Core.dll` with `Add-Type -Path`), then start it; `-LockOnly` for runs that never unlock; `@{ gone = 90 }` waits for the lock screen to close (Windows Hello needs a person at the PC). After a lock or restore restart, `@{ adopt = 30 }` follows the new process and `@{ lock = @(...) }` drives its lock screen; `@{ tray = 'Lock now' }`, `@{ globalkey = 1500 }`, `@{ press = 'ctrl+l' }`, `@{ close = 1 }` and `@{ log = 'text' }` exist too. Give each run its own `-Port` if an earlier one may still be running.

## How polish features work (M7)

- **Assistants and prompts:** `DogAI.Core/Library`. `LibraryCatalog` keeps both lists as JSON documents in the settings store (keys `assistants`, `prompts`; a first run gets starters, and deleting them all is respected). Starting a chat from an assistant copies its instructions and style into the chat (`Components/Library/AssistantPanel`). Prompt blanks are `[[name]]` / `[[name|default]]` (`PromptVariables`), not `{{ }}`, which character cards use. The composer's book button opens `PromptPicker`.
- **Search:** `DogAI.Core/Search` (`ChatSearch` builds the FTS5 query from typed words and cuts snippets; `ChatHit`; `ChatExport`), `SqliteSearchStore` in Data. The `MessageSearch` FTS5 table lives only in the `Polish` migration's raw SQL, kept current by three triggers on `Messages`; EF does not know it. Snippets mark matches with control characters; draw them with `ChatSearch.Parts` as text, never as markup. A hit opens through `ChatService.SelectBranchAsync`, then `chat.js` `scrollToMessage` finds `[data-mid]`. Story route ids are conversation ids.
- **Chat folders (General only):** `ChatFolder` and `ChatFolders` (Core/Chat: `CleanName`, `Named`, `Arrange` sorts the list into pinned, folders, loose). `Conversation.FolderId` has no foreign key (avoids a table rebuild); `IChatStore.DeleteFolderAsync` clears it. `UpdateAsync` never touches the folder; use `SetFolderAsync`.
- **Backup and restore:** `DatabaseBackup` (Data) behind `IBackupService` (Core). Backup is `VACUUM INTO` plus `backup.json` in a zip. Restore only stages (`restore\dogai.db`); `App.OnStartup` calls `DatabaseBackup.ApplyPending` before anything opens the database. `IDesktopShell.Restart()` relaunches with `--after <pid>` so the new process waits for the old. New machine-specific settings go in `DatabaseBackup.MachineSettings` so a restore keeps this PC's values.
- **Code colours and maths:** `DogAI.UI/wwwroot/vendor` (highlight.js, KaTeX, with licences and checksums in `vendor/README.txt`) and `js/enhance.js`, loaded from `index.html`. `MarkdownView` writes each code block as one HTML-encoded markup piece with `data-lang`; `MarkdownRenderer` has `UseMathematics`, which marks formulas `.math`. Do not make Blazor render the inside of a block that JS colours.
- **Links:** `LinkGuard` (in `MainLayout`, inside the `.shell` div so it gets the theme) listens through `chat.js` `watchLinks` and asks before `IDesktopShell.OpenUrl`. Any new modal must also sit inside `.shell`.
- **Windows extras:** `DogAI.App/WindowsIntegration` (tray icon via WinForms `NotifyIcon`, close-to-tray, the Ctrl+Alt+Space low-level hook on its own thread; text arrives through `Dictation.HeardForOtherPrograms`). Settings: `TrayIcon`, `CloseToTray`, `DictateAnywhere`, all off by default.
- **Publish:** `dotnet publish src/DogAI.App -p:PublishProfile=win-x64` writes `publish\win-x64`: a small launcher `DOG.ai.exe` (project `DogAI.Launcher`, only starts `app\DOG.ai.exe`), `portable.txt`, and `app\` with every program file. Targets in `DogAI.App.csproj` drop other platforms' native files, empty `app\` before publishing (only a folder named `app`, never the root, so `data\` and `models\` are safe), and publish the launcher and marker into the root. Check a publish by running the exe in `app\` (not the launcher, which exits at once): `tools/walkthrough.ps1 -Exe <path to app\DOG.ai.exe> -Portable`. `tools/tidy-install.ps1` converts an old flat install (program files loose beside `data` and `Models`) to this layout.
- **Portable mode:** a `portable.txt` next to DOG.ai.exe, or one level above it when the exe sits in a folder named `app` (the publish layout; never in Debug builds), makes `AppPaths.ForProgram` put data in `<home>\data` and models in `<home>\models`, forced on every start. `DOGAI_DATA_DIR` still wins (test runs). Portable runs point the process's TEMP/TMP at `data\temp` (inherited by llama-server and native libraries), and `LlamaServerLocator` uses only `data\engine` (no winget/PATH fallback; `DOGAI_LLAMA_SERVER` still wins). `PortableMove` (Data) rewrites saved paths in the Settings JSON and `ModelRecords` when the folder moved (`data\home.txt` records the last home). Any new setting or table that stores a full path must be added to `PortableMove`. Walkthrough: `tools/walkthrough.ps1 -Exe <copy>\app\DOG.ai.exe -Portable`.
- **Tool quirk when writing code through the shell:** doubled backslashes can be collapsed and `\n` in Python strings can turn into real newlines; use the Edit/Write tools for C# or JS that contains escapes.

Check every new screen in all three skins, dark and light. Say plainly what was and was not looked at. Never point a test run at the real data folder (`%LOCALAPPDATA%\DOG.ai`), and never run a portable walkthrough from the owner's real portable folder; copy `publish\win-x64` somewhere temporary first.
