- **Removed means gone from the database files (2026-11-14, after M9 step 5; the owner's decision).** What the owner deletes (a chat, a story, a character, a persona, a document, a kept picture) no longer stays readable in a plain database's files. With the lock on it was never readable; this is for a database without the lock.
  - *What was really wrong.* Step 5 reported that a removed picture could still be found, and suggested switching on SQLite's "secure delete". That was only partly right: **secure delete has been on since M8** (the SQLite build DOG.ai ships is compiled with it), so the database file itself already overwrote deleted content with zeros. The removed picture was in the **log file beside the database** (`DOG.ai.db-wal`), which keeps earlier versions of changed pages while DOG.ai runs and after a crash. Looking further found a second place: the **search index** kept the words of deleted messages (seen in the file: the words of a deleted reply, in order).
  - *What was done.* (1) Shortly after any delete (0.7 seconds after the last of a burst) DOG.ai folds the log file into the database and cuts it to nothing (`DatabaseTidy`, told by a watcher on every database command); it is also done once after each start. It never fails or slows the delete itself, and tries again a few times if the database is busy. (2) A migration (`SearchWipe`) turns on the search index's own secure delete, so a deleted message's words leave the index at once, and rebuilds the index from the messages that exist, which drops the words of chats deleted earlier. (3) A test pins that the SQLite build has secure delete on, so a package update cannot lose it silently.
  - *Checked.* `dotnet build`; `dotnet test` (749 pass, 10 new; the whole suite passed six times in a row, after two of the new tests' own file searches were made tolerant of SQLite removing its log files mid-search): with DOG.ai still open, a removed picture's bytes and prompt, a deleted chat's words (any case, UTF-8 and UTF-16, title, messages and search index), and a deleted character's text, chats and pictures are in no file of the data folder, while what was not deleted is still there and still found by search; the same for messages written before this change, and for a chat deleted before this change once the update has run; several deletes are tidied once and DOG.ai goes on working; a delete just before closing leaves nothing; a locked database's log file is emptied too; the download token taken out of a backup is not in the backup's bytes. **In the app:** the plain leak-check walkthrough run again (four pictures drawn, one kept, one kept and removed, one cancelled): the removed picture and its LoRA's trigger word are found nowhere, the log file is 0 bytes, and the kept picture and the marker are found in the database (the control).
  - *Not checked, and limits.* A deleted **chat** in the running app (tests only; the picture was removed in the app). The time the search index takes to rebuild at the first start on a large database (it reads every message once). Changing something (a card's text, a setting) is not a delete: the earlier version can stay in the log file until the next delete, the next start or a normal close. A crash in the fraction of a second between a delete and the tidying leaves it in the log file until the next start. On an SSD the emptied log file's space is freed, not overwritten, like any deleted file. Things deleted before M8's SQLite build (13 November) may still sit in unused space of a plain database until SQLite reuses it; turning the lock on, or restoring a backup, rewrites the file without it. Backups and exports made earlier hold whatever they held.
- **M9 step 5, keeping pictures (2026-11-14).** DOG.ai can now keep a picture safely: inside the database, with everything needed to draw it again. Nothing in the app keeps pictures yet (portraits are step 7, story illustrations step 8); the owner sees no change except that the test picture on Models → Images is now drawn the way pictures will be kept.
  - *What exists.* A `Pictures` table (an additive migration; nothing existing is rebuilt). Each kept picture holds the image as WebP, its size, and how it was drawn: checkpoint, separate VAE and v-prediction, prompt and negative prompt, size, seed, steps, sampler, scheduler, guidance, clip skip, LoRAs with strengths, hires fix, and when it was made. Files are named by their path inside their own folder (`illustrious/nova.safetensors`), never a full path; the store refuses a full path, a path that climbs out of its folder, and anything that is not a whole WebP file. `IPictureStore` (Core) has add, read (with or without the image), list by owner (newest first, without the images so a list stays light), delete one, delete all of an owner's; `SqlitePictureStore` (Data) is the real one. `Picture.Of` turns a finished drawing into a picture to keep, `ToRequest` and `ModelIn` give back the request and the model to draw it again.
  - *What a picture belongs to* is a kind plus an id: `character`, `persona`, `message` (a story passage is a message; chat replies can use the same later) and `test`. The kind is plain text, so steps 7 and 8 can add kinds with no migration. **The database itself removes pictures when their owner is deleted** (three triggers: a message, also when its whole chat or story is deleted; a character; a persona), so no code path can leave pictures behind. A new kind that has its own table needs its own trigger.
  - *WebP quality: 90.* Five pictures from the owner's checkpoint (portrait, night street with neon signs, close-up face on white, a Fine picture at 1280×1856, a painterly LoRA picture) were each drawn from one seed as PNG and as WebP at 70, 80, 85, 90, 95 and 100, then compared against the PNG by eye at four times enlargement, with a difference map beside each. At 70 thin neon strokes smear. At 80 the fine lines in an iris are gone and hair highlights soften. At 85 the iris lines are fainter. **At 90 I could see the difference only on the difference map, not in the picture.** 95 costs 55 to 80% more bytes for nothing I could see, and 100 is still not lossless (the slight colour softening of very thin saturated lines is the format's, at every quality). Sizes at 90: 92 to 113 KB at 832×1216 or 1024×1024, 170 KB for the busy night scene, 174 KB for the Fine picture, against 1.5 to 3.5 MB as PNG. 85 would save about a quarter, which is not worth it for pictures that get opened large and cropped into avatars. The engine makes the WebP itself, so DOG.ai needs no picture library; it writes nothing inside the file (checked: no EXIF or XMP part).
  - *The lock, backups, restore and portable mode needed nothing new*, as planned. Tests: the bytes of a picture and its prompt can be found in a plain database file and cannot once it is encrypted, nor in the log file beside it while the app is writing; a database locked from its first day never holds them in the clear; a backup and restore bring pictures back byte for byte in all four cases (plain or locked backup into plain or locked DOG.ai), with nothing readable waiting on disk whenever either side is locked; a locked backup's description says nothing about pictures; moving a portable folder rewrites only the settings row and the picture finds its files under the new models folder.
  - *The picture engine's lines now reach DOG.ai's log* (`picture engine: …`, about 15 to 25 lines a picture: model loading, timings, the seed, hires and LoRA steps, errors) through a filter with two separate rules once any prompt has been sent. (1) Only status lines pass: the ones the engine marks `[I]`, `[W]`, `[E]`, and graphics-library messages such as out of memory. Detail lines (`[D]`, where the engine would print prompts), progress bars and anything unrecognised are dropped. (2) A status line that shares a word with a prompt or negative prompt sent in the last ten minutes is held back, also when the word sits inside a longer one or is cut short; the engine forgets a finished picture after one minute. The log then says how many lines were held back, never what they said. The price: an ordinary line that happens to contain a prompt word is lost too (seen for real: the LoRA loading lines for `Maid_marian.safetensors` when `maid_marian` is in the prompt). The engine's raw output is still never logged.
  - *On screen.* The test picture is now drawn as WebP at 90 (was JPEG). **Keep this picture**, the kept pictures and **Remove** / **Draw again and compare** exist under it only when `DOGAI_TEST_PICTURE_WORDS` is set (it also adds those words to the test prompt): a switch for checking, not something the owner sees.

- **M9 step 3, sharing the graphics card (2026-11-14).** The chat model and the picture model now take turns on the graphics card by themselves. There is still nothing to draw with in the app (steps 4 to 8); what the owner can see is the chat model marked "set aside" after a picture and coming back with the next message.
  - *What exists.* `CardCoordinator` (Core/Images) is the picture engine the whole app gets (`IImageEngine`); the real `ImageServer` sits behind it, so no picture can be drawn without it. Before each picture it works out what the picture needs (`PictureMemory.Need`: the checkpoint file plus a quarter, the LoRAs' sizes, and 4 GB per million pixels of the largest pass, which gives 12.1 GB for Standard and 17.6 GB for Fine with the owner's checkpoint), measures the card (`CardMeter`: total and free memory, and what each engine holds), and decides: if the need, less what the picture model already holds, fits in free memory with 1 GB to spare, both stay; otherwise the chat model is **set aside**. A card that cannot be measured gets the swap.
  - *"Set aside"* is a new state of the chat engine (`EngineState.Resting`, `EngineManager.RestAsync`): its program ends and the memory comes back, but the model, its context size and its settings are remembered. Chat pages treat it as ready (`IsReady`), so the message box and every button work; the first thing that really asks the model (a reply, a prompt being measured) loads it again exactly as it was. It is **not** the owner's Unload: the owner's hold in `ModelLauncher` is untouched, a model the owner unloaded is never loaded by the coordinator, the owner's **Unload** on a model that is set aside forgets it for good, opening a page does not load a default over it, and the unload-when-unused timer leaves it alone (it holds no memory).
  - *One swap for a run of pictures.* After the picture the chat model is not loaded again. "Try again" and further pictures find nothing to move. The next message brings it back, and the picture model (which stays chosen) is let go first unless both are measured to fit.
  - *Nothing races.* One thing at a time changes what is on the card ("a turn"). A picture waits for a reply that is being written (the reply is never cut off) and for a chat model that is loading. **A chat request that arrives while a picture is drawing waits** for the picture, then for the model to load, and is then answered. Decided against a plain "try again later" message because a picture takes seconds, and a message that was already sent would otherwise sit unanswered until the owner pressed Answer; Stop still works while it waits. Loading a model by hand and benchmarking wait in the same way, and let the idle picture model go first, so that what fits is measured against a card without the picture model's 8 GB on it (otherwise part of a big chat model would be pushed off the card).
  - *Idle time of the picture model: 2 minutes* (was a 5-minute placeholder), counted from the end of the last picture and checked every 15 seconds. Why: keeping it costs 8 GB, a third of the card, and getting it back costs about 4 seconds; two minutes covers looking at a picture, changing the prompt and drawing again. The chat model never waits for this timer.
  - *Idle lock.* `AppLock` counts the picture engine's `IsBusy`, which is true from the moment a picture is asked for (waiting, making room, drawing) until it is finished or has failed.
  - *On screen (no more than needed to see it).* The model button says "· set aside" with an amber dot; the model picker says the model "was set aside to make room for pictures. It loads again by itself with your next message", with **Unload**; Workbench's status bar says the same; Models → Engine has a **Now** line for the picture engine. Two test buttons (**Draw a test picture**, **Draw a fine one**) appear on Models → Engine only when `DOGAI_TEST_IMAGE_MODEL` names a checkpoint; step 4's Images tab replaces them. The character editor's token count no longer asks a model that is set aside.
  - *Measured with the real engines* (RTX 4090, card otherwise at 0.8 to 1.2 GB; the owner's 27B model read where it is, the sample checkpoint read where it is, the trial's copy of the picture engine through `DOGAI_SD_SERVER`, nothing downloaded): the 27B at 8,192 context holds 17.0 to 17.2 GB, leaving 5.2 to 5.8 GB free. First picture: chat model set aside, picture drawn in 12.6 to 14.4 s (6.3 s without a swap); afterwards 8.5 GB in use (picture model 7.3 GB). Second picture: no swap, 6.3 s, card peaks at 12.1 GB in use. Next message: picture model let go, 27B loaded again in 30 s and answering after 31 to 37 s, back at 17.0 GB (whole, not squeezed). A Fine picture (832×1216 with hires fix ×1.5 comes out 1280×1856, not 1248×1824): swap again, 21 s, card peaks at 17.7 GB. With a 7 GB chat model (8.0 GB on the card) **both stay loaded**: no swap, card peaks at 20.1 GB, pictures in 6.5 s, the next reply starts at once. This is the test the trial did not run.
  - *Checked.* `dotnet build`; `dotnet test` (669 pass). New tests with fakes: both fit; do not fit; a run of pictures costs one swap and the next message brings the model back; the picture model stays when the returning model fits; Fine needs the swap when Standard does not; an unmeasured card; a model the owner unloaded stays unloaded (before a picture, and while set aside); a chat request during a picture waits and is answered, and can be stopped; a model loaded by hand during a picture waits and gets a free card; a picture waits for a reply and counts as busy all along; cancelling a waiting picture; one picture at a time; a bad request moves nothing; LoRAs count; the estimates against the trial's numbers. `CardSharingSmokeTests` runs the real engines when `DOGAI_TEST_MODEL`, `DOGAI_SD_SERVER` and `DOGAI_TEST_IMAGE_MODEL` are set; run with the 27B (swap) and the 7 GB model (both stay), including the owner's Unload while set aside. **In the app** (three walkthroughs on throwaway data folders, graphics memory sampled twice a second from outside): the 27B loaded and answered, picture, "try again", General showing "set aside", next message answered by the 27B, Fine picture; then the set-aside notice in all three looks, dark and light, with Characters, Story, Settings and Models opened and nothing coming back (no llama-server process), and the picture engine gone after its two idle minutes; then a locked data folder with a 20-second idle lock: it stayed open through a 17-second picture and locked within a second of the picture finishing ("nobody used the PC for 22 seconds").
  - *Not checked.* Only with fakes, because nothing in the app can do it yet: a picture asked for while a reply is being written, a chat request sent while a picture is drawing, a model loaded by hand during a picture. Not tried at all: **Stop** pressed while the model is coming back (by design the reply stops and the load carries on); the owner's **Unload** clicked in the app while set aside (the real-engines test does it through the same code); a model that cannot come back (file gone, or another program has taken the card: the engine's own error would show); a benchmark with the picture model loaded; group chats, stories and the document search model alongside pictures; LoRAs in a real picture through the coordinator (they are counted by file size, not measured); picture sizes other than 832×1216 (the "4 GB per million pixels" is drawn from two measurements); the portable build. **Known limit:** when another program holds a lot of the card (a game, Ollama with a model loaded), setting the chat model aside may not be enough; the picture is drawn anyway and will be slow or fail, with no plain message yet.   - *For later steps.* Draw only through `IImageEngine` from the app's services (never `ImageServer`), and after the chat model's prompt job has ended, not from inside a streaming request: a picture that needs the room waits for the request to finish. Show the two extra progress stages (`CardCoordinator.Waiting`, `MakingRoom`). Use `EngineManager.IsLoaded`, not `IsReady`, for anything passive that should not bring the model back (counting tokens while typing). Embedding models are recognised from their header, are not offered for chat, and have no Load or Benchmark buttons. Changing the model indexes every document again in the background.

- **How M5 behaves, decided while building it:**
  - *Found passages and recalled messages go with the newest user message, never in the system message.* llama-server reuses the prompt it processed last time up to the first change; text that changes every turn in the system message would mean reading the whole chat again for every reply. The standing "cite the passages" instruction stays in the system message, since it does not change.
  - *Search combines meaning and exact words.* Passages are ranked by vector similarity and by keyword scoring (BM25) and the two rankings are merged, so a code like "E4012" or a name is found even when the meaning score alone is weak.
  - *Thresholds were measured, not guessed:* with Qwen3 Embedding 0.6B a question and its answer passage scored 0.55–0.75, other passages of the same documents 0.27–0.43, unrelated text under 0.2. Passages need 0.45 (or 0.25 with a strong exact-word match); recalled messages need 0.5, because a wrong memory misleads more than a missing one.
  - *Passages are short (about 800 characters).* The first live try used 1,200 and a whole PDF page that mixed maintenance, error codes and warranty scored 0.28 against a question it answered.
  - *The passage list says which numbers exist* ("numbered 1 to 3"). Without it the model also cited the manual's own section numbers ([4], [5]); numbers that are not sources stay plain text.
  - *Vectors belong to one model.* Each is stored with the model's file name and only compared with vectors from the same model. Messages are embedded the first time recall needs them and again only if edited.
  - *"Open the file" opens documents in their usual program, but code and scripts in Notepad*, so opening a .bat or .ps1 shows it rather than running it.

## Context

`C:\Claude\DOG-AI` is empty and not a git repo, so this is a greenfield build.

**Your machine (measured):** RTX 4090 (24 GB VRAM), Core Ultra 9 285K (24 cores), 32 GB RAM, VS 2022 Pro 17.14 with the .NET desktop workload, .NET SDK 9.0.320. `D:` is empty (931 GB free); `C:` has 184 GB free.

**Engine.** One `llama-server` child process per loaded model, bound to `127.0.0.1` on a random port, plus a small second instance for embeddings. The app talks to it over its HTTP API: streaming chat completions, `/tokenize` for exact token counts, `/apply-template` + `/completion` for continue/prefill, and JSON-schema-constrained output for structured results. Chat templates come from the GGUF itself. Idle auto-unload frees VRAM. On first run the app can adopt the `llama-server` you already have from winget until its own copy is downloaded.

**Offline guarantee (enforced, not just promised).**
- All `HttpClient` use sits behind one gateway in `DogAI.Hub`, gated by an "Online" switch that is off by default and only turns on inside the Models section.
- WebView2 is restricted to the app's own origin; any other request is blocked and logged. Links open in your browser only after a confirmation.
- Imported card and document text is treated as untrusted: markdown renders with raw HTML disabled.
- No telemetry, no update checks outside the Models section.

**Data.** SQLite. Messages are stored as a tree (each has a parent), which gives regenerate, swipes, edit-and-branch, and CYOA branching from one mechanism. Embeddings are stored as blobs with in-memory cosine search, which is plenty for single-user scale.

## M9: Pictures (planned 2026-11-13; steps 1 to 5 done)

DOG.ai draws pictures on this PC with **stable-diffusion.cpp**, a sibling of llama.cpp, run the same way as the chat engine: a child process on `127.0.0.1` that DOG.ai starts and stops. Nothing goes online to draw.

**Decisions the owner made (2026-11-13):**
- stable-diffusion.cpp as a second engine (not ComfyUI, not ONNX, not an online service).
- First version supports the **SDXL family only** (Illustrious, NoobAI, Pony, base SDXL): one checkpoint file each, plus LoRAs.
- Pictures are made in two places: **character and persona portraits** and **story illustrations**. A picture button in chats and a standalone Images screen are later steps.
- **Civitai files are added by hand** (downloaded in a browser, dropped into the image models folder). **Hugging Face downloads happen in the app**, as for chat models. Civitai is not added to the allow-list.
- After the chat model writes a picture prompt, DOG.ai **draws at once** by default; a switch in Settings makes it **show the prompt first**.
- The owner supplies an Illustrious checkpoint and LoRAs for the trial.
- LoRAs can be **character LoRAs as well as style LoRAs**: a card can carry its own, and a checkpoint can have style LoRAs that apply to every picture.
- Default shapes: **Tall** for portraits, **Wide** for story illustrations.
- **No automatic illustrations**; pictures are made only when asked for.
- A story picture shows **at most two or three people**.
- Prompt wording follows the checkpoint, with no switch to flip per picture: **Danbooru-style tags** for Illustrious, NoobAI and Pony, sentences for base SDXL. The checkpoint's quality words ("masterpiece, best quality…", Pony's score tags) and negative prompt are added by DOG.ai, never left to the chat model.

**What was read about the engine (2026-11-13, from its documentation, not yet run here):**
- It ships a server program, `sd-server.exe`, with its own API: start a picture (returns a job), ask a job for its progress and a small preview, cancel a job, list what it can do, load and unload a model without exiting. Pictures come back in the reply, not as files; PNG, JPEG or WebP.
- LoRAs are given per picture as a list (file and strength). `<lora:...>` tags typed in a prompt are **not** read by the server, so DOG.ai picks LoRAs in its own controls.
- Per picture: clip skip, sampler, steps, "hires fix" (draw, enlarge, refine). Per loaded model: the VAE. A face-detail pass is mentioned but not documented. V-prediction is not in the server's documentation: **the trial must settle it.**
- Windows downloads are a CUDA 12 zip plus a separate zip of NVIDIA runtime files. MIT licence.
- The server has a built-in web page. It will listen only on `127.0.0.1` on a random port, like llama-server.

### Trial results (step 1, 2026-11-13)

Run by hand on this PC, outside DOG.ai: engine build `master-1094-3bad892` (CUDA 12 zip plus the NVIDIA runtime zip, both SHA-256 checked against the release page; about 1.2 GB unpacked, most of it NVIDIA libraries), the owner's checkpoint `illustrious_novaFurryXL_ilV180A` (6.6 GB, recognised as SDXL, eps-prediction) and three LoRAs (detail, style, character; all plain LoRAs of 218 MB). 25 pictures drawn; seven looked at.

- **It works, and the pictures are good.** The first try (tags: silver hair, green eyes, scar on cheek, leather armor, green cloak, forest, dappled sunlight) showed every tag, with no black-picture VAE problem and no extra VAE file needed.
- **Speed (832×1216):** Draft (20 steps) 5 s; Standard (28 steps) 6.5 s; Fine (28 steps, hires fix ×1.5 with 14 more steps) 14 to 15 s, giving 1248×1824. About 5 steps a second. The very first picture after a start takes about 4 s longer (the model is read into graphics memory then, not at start, so the server itself is up in under a second). Four pictures in one request: 25 s.
- **Graphics memory (above what Windows already uses):** about 8 GB held while the model is loaded and idle, about 11.5 GB at the peak of a Standard picture, about 17 GB at the peak of a Fine one. Unloading through the API gives it all back without stopping the server.
- **Beside the chat model: no.** The owner's 27B chat model is a 16.8 GB file, so the two cannot both be on the card; this is arithmetic, not a test (the test was not run). The swap in "Sharing the graphics card" is needed every time with this chat model, and Fine quality needs the card nearly to itself. *(Step 3 ran it: the 27B holds 17 GB and is set aside for every picture; a 7 GB chat model stays loaded beside the picture model, the card peaking at 20.1 GB.)*
- **LoRAs:** each worked alone and all three together. The character LoRA with its trigger word gave the same character in two shapes and seeds; without the LoRA the same prompt gave a generic one. Changing the LoRA set costs about 3 s on the next picture (about 10 s for three at once); going back to none also works. Trigger words and the most common training tags can be read from the files' own metadata.
- **Cancel** stopped a 60-step picture within about 0.3 s, and the next picture was normal. **Preview** ("proj" mode needs no extra file) gave a new small picture every few steps. Progress reports the stage (conditioning, sampling, decoding, encoding) and the step.
- **Hires fix** makes a visibly sharper picture but can change small things (it drew a second scar). So Fine is for a picture already chosen, not for trying ideas.
- **Picture size on disk:** PNG about 1.7 MB (3.6 MB for Fine), JPEG at 92 about 255 KB, WebP at 90 about 128 KB. Decision for storage: **WebP**, with the quality number fixed in step 5 after comparing by eye (not compared closely yet). *(Step 5 compared them: quality 90; see Status.)*
- **Privacy:** the server wrote **no file** to its working folder or its temp folder in the whole run, and at its normal log level the prompt does **not** appear in its output (model path, timings and step counters do). Its verbose level was not tried and must never be switched on by DOG.ai. `--disable-image-metadata` exists, so the prompt need not be embedded in a picture that gets exported.
- **V-prediction:** the engine has a load option for it (`--prediction v`). Not tried: the owner's checkpoint is the normal kind. Needs a v-prediction checkpoint to confirm.
- **More than planned is there:** a face-detail pass (needs one small extra detection model), reference-picture control for SDXL (IP-Adapter), image-to-image and inpainting. None are in M9, but they are no longer blocked by the engine.
- **Not tried:** drawing while a chat model is loaded; loading a different checkpoint through the API (only unloading was tried; the first load was from the command line); a separate VAE file; LyCORIS-type LoRAs (none in the samples); face detail; verbose logging; the engine under DOG.ai's portable temp folder.
- **Suggested starting numbers for this family** (to be tuned in step 6): Euler a, guidance 5.5, clip skip 2, quality words "masterpiece, best quality, amazing quality, very aesthetic, absurdres", negative "worst quality, low quality, bad quality, lowres, bad anatomy, bad hands, jpeg artifacts, signature, watermark, text".

### How it will work

**Engine (`DogAI.Engine/Images`).** `ImageServer` follows `EmbeddingServer`: started the first time a picture is asked for, random loopback port, `EngineEnvironment.Clean`, `ProcessJob` so it dies with DOG.ai, stopped when idle. It is found by its own locator in `data\engine` (override `DOGAI_SD_SERVER` for tests), and Models' engine updater gets a second entry that downloads it from the project's GitHub releases (one new allowed path in `OriginPolicy`, checksum checked). *Built in step 2: it lives in `data\engine\images`; no `OriginPolicy` change was needed (GitHub's hosts were already allowed); a checkpoint is loaded by starting the program with it, because the API's load works only inside the server's own folder layout (see Status).* Core sees only an `IImageEngine` interface, so tests use a fake.

**Sharing the graphics card.** A 27B chat model and an SDXL model do not fit in 24 GB together. A small coordinator decides per picture: if both fit (measured free memory), keep both; otherwise the prompt is written first, the chat model is unloaded, the picture is drawn, and the chat model is loaded again **only when it is next needed** (not straight away, so "Try again" and a run of pictures cost one swap, not one each). The image model is let go after a short idle time. A chat model the owner unloaded by hand stays unloaded. *Built in step 3: the coordinator is the picture engine the app hands out; the chat model is "set aside" rather than unloaded, so chat pages keep working and the next message loads it again; a chat request during a picture waits for it; the picture model's idle time is 2 minutes (see Status).*

**Image models folder.** `<models>\image\checkpoints`, `\loras`, `\vae`, `\upscalers`. Only `.safetensors` is accepted; the old `.ckpt` format can carry program code and is refused with a plain message. DOG.ai reads each file's header to tell what it is (SDXL checkpoint, SDXL LoRA, something else) and shows files it cannot use as such.

**Models → Images tab.** Installed checkpoints and LoRAs, **Open folder** (for Civitai files), recommended downloads from Hugging Face, the image engine's install and update. Each checkpoint has a small settings card so pictures come out right without fiddling: prompt style (tags or sentences), the "quality" words it wants before and after a prompt, the negative prompt, sampler, steps, guidance, clip skip, normal or v-prediction, and its VAE. Known families get these filled in when the file is recognised; the owner can change them. Each LoRA has its trigger words (read from the file when it has them) and a default strength.

**Looks on a card.** Characters and personas get a **Looks** box: appearance tags ("silver hair, green eyes, scar on left cheek…"), and optionally a LoRA with its strength. The chat model can draft the tags from the card's description. Stored in the card's extra data so export and import keep it. This is what keeps a character recognisable from one picture to the next.

**Writing the prompt (`DogAI.Core/Images`).** A DOG.ai model job (schema-constrained, checked before use, thinking off) turns a card or a story passage into the pieces of a prompt in the checkpoint's style. The final prompt is assembled by code, not by the model: checkpoint quality words + the Looks of the people in the scene + scene tags + the checkpoint's negative prompt. For a story, the people are the passage's cast (`StoryPrompt.People`), at most two or three (SDXL handles more badly, and the plan says so in the app).

*Tag prompts.* For tag-style checkpoints the model does not write a free prompt. It first picks **one moment** of the passage that can be shown as a still picture, then fills named slots: who is in it (as a count, "1girl, 1boy"), clothing, expression, pose or action, place, time and light, framing ("upper body", "from above"). Code puts the slots in the order these checkpoints expect and adds each person's Looks from their card (so the model cannot change a character's hair colour). Every tag is checked against a **bundled list of real Danbooru tags** (shipped with DOG.ai, no lookup online): near misses are corrected to the real tag, unknown ones are dropped, and the prompt is kept short. Where the list comes from and its licence are settled in the trial. What this does well: one or two people, their looks, clothes, mood, place and light. What it does poorly, said plainly in the app: exact actions between people, one person's features leaking onto another, unusual objects, anything that depends on what happened earlier in the story.

**Quality choices.** Three named levels in place of raw numbers: **Draft** (fast, for trying ideas), **Standard**, **Fine** (hires fix, and face detail if the trial shows it works). Shapes: Tall, Square, Wide, using SDXL's native sizes. A live preview and step count while drawing; **Cancel** works mid-picture. Every picture keeps its seed and settings, so **Edit and redraw** changes one thing and keeps the rest. Raw settings stay available behind "More".

**Portraits.** **Generate picture** in the character and persona editors opens the picture maker (shared component in `Components/Images/`): Draw, Try again (variations side by side, held in memory), Edit and redraw, **Use this picture**, which hands the result to the existing cropper. Nothing is saved until Use.

**Story illustrations.** **Illustrate** in a passage's actions. The picture sits above the passage, opens large on click, and can be redrawn or removed. Which picture belongs to a passage is recorded through `StoryTurn`. HTML and EPUB exports include the pictures; Markdown does not.

**Keeping pictures (and keeping them private).** Kept pictures go **inside the database** (a new `Pictures` table), so the lock, backups, restore and portable mode cover them with no new machinery. They are stored compressed (the trial compares PNG and WebP for size and looks); tried-and-discarded variations never touch the disk. The image engine is started so that it writes no picture, prompt or preview to disk, and DOG.ai's log never records a prompt (the engine prints prompts in its own output, so those lines are filtered). Drawing counts as "busy" for the idle lock. *Built in step 5: WebP at quality 90, made by the engine itself; the engine's own lines reach the log through a filter (it prints no prompt at its normal level, and the filter holds if a later version does); see Status.*

**Settings → Pictures.** Default checkpoint, default quality, "Show me the prompt before drawing" (off by default), and the **rating** pictures aim for (owner's decision 2026-11-13: a setting, not the chat model's choice). The rating tag is added by code, the tags for anything above the chosen rating go into the negative prompt, and the prompt job is told the rating so it picks a moment that fits. Which rating words each family uses (Illustrious, NoobAI, Pony differ) sits on the checkpoint's settings card.

## M8: Locked data (built 2026-11-13)

Part 1 (the machinery and a plain lock screen) and part 2 (the screens, locking, the leak checks) are recorded in Status at the top, with what was checked. Where building it changed or settled something in the plan below, the text says so in *italics*.

**Goal.** Without the password, nobody can read anything DOG.ai keeps: not on this PC, not from a copied data folder, not from a backup zip, not from a lost USB stick holding a portable copy. It is off by default and turned on in Settings.

**What it does not protect against, said plainly.** Malware running as the owner while DOG.ai is unlocked; someone at the PC while it is unlocked; Windows' own traces (listed under Portable mode above). Model files are not encrypted: they are public downloads and say nothing about the owner.

### How it works for the owner

- **Turning it on** (Settings → Privacy → Lock DOG.ai with a password): choose a password, then DOG.ai shows a **recovery key** (24 letters and digits in groups) to print or write down, and asks for part of it back before going on. The database is then encrypted in place; this takes seconds to a minute.
- **Starting DOG.ai** shows only a lock screen: the password box, **Use Windows Hello** if it is set up on this PC, and **I forgot my password** (asks for the recovery key, then a new password). Nothing else loads until it is unlocked: no chats, no tray menu, no Ctrl+Alt+Space, no default model.
- **Windows Hello** (face, fingerprint or Windows PIN) is offered after the first unlock on each PC. It is per PC: a portable copy on another PC asks for the password once, then offers Hello there too.
- **Locking:** **Lock now** (Settings, the tray menu, Ctrl+L), and after an idle time chosen in Settings (off, 5, 15, 30, 60 minutes; default 15). Locking restarts DOG.ai into the lock screen (`IDesktopShell.Restart`), which is the only sure way to clear the key and every decrypted chat from memory. A loaded model is unloaded by that restart; the default model loads again after unlocking.
- **Wrong passwords:** after five wrong tries in a row, each further try waits longer (30 s, then 1 min, then 5 min). Nothing is ever wiped.
- **Changing the password** is instant (only the key wrapping changes, not the database). **A new recovery key** can be made at any time; the old one stops working.
- **Turning it off** asks for the password and decrypts the database back to a plain file.
- **Forgotten password and lost recovery key:** the data is gone for good. The setup screen says this in one plain sentence, and so does the "forgot" screen.

### How it works inside

- **Library:** SQLite3 Multiple Ciphers (MIT licence) through its SQLitePCLRaw bundle, in place of the plain `e_sqlite3` bundle EF Core uses now; the key is passed through the connection string's `Password`. The default cipher (ChaCha20-Poly1305) is used. To be checked first, before any other work: that its bundle matches the SQLitePCLRaw version EF Core 9 uses, that FTS5 (`MessageSearch`) works, and that every existing test passes on it unchanged. If any of these fails, stop and report rather than switch libraries silently. *Outcome: the bundle is `SQLite3MC.PCLRaw.bundle` 2.6.1 (needs SQLitePCLRaw 3.0.2), and Microsoft.Data.Sqlite is raised to 10.0.15 because 9.0.23 cannot reopen an encrypted database through `Password`; the owner approved both. FTS5 works and every existing test passes. The key is passed as a raw key (`raw:` plus 64 hex digits), which skips the library's own password stretching on every open.*
- **Keys:** a random 256-bit database key. It is never stored as it is; it is stored wrapped (AES-GCM) three ways in a small plain file beside the database, `lock.json` (it must be outside the database, because it is read before the database can be opened):
  - by a key derived from the password (PBKDF2-SHA256, 600,000 rounds, random salt; built into .NET, no new package),
  - by a key derived from the recovery key, the same way,
  - by Windows Hello, one entry per PC: a Hello key (`KeyCredentialManager`) signs a fixed challenge, and the signature is turned into a wrapping key. Hello keys are RSA with PKCS#1 v1.5 signatures, which are the same every time for the same challenge, so this works without storing any secret; Windows asks for the face, fingerprint or PIN each time. To be confirmed on this PC at the start of M8; if the signatures differ, Hello falls back to a DPAPI-wrapped key released after a Hello check (weaker: anything running as the owner could unwrap it), and the plan is brought back to the owner before going on. *Confirmed on this PC: same bytes every time; the fallback is not used. The signature goes through HKDF-SHA256 with a per-entry salt to make the wrapping key. One Hello key ("DOG.ai data lock") serves every DOG.ai data folder in a Windows account; each folder has its own challenge.*
  - `lock.json` holds salts, round counts and wrapped keys only; nothing in it opens the database without the password, the recovery key or the owner's Hello.
- **Core** (`DogAI.Core/Privacy`): `LockFile` (read, write, wrap, unwrap, change password, new recovery key), `RecoveryKey` (make, format, read back with spaces and dashes forgiven), `UnlockThrottle` (wait times). All testable without Windows Hello; Hello sits behind an interface implemented in App.
- **Start-up order** in `App.OnStartup`: pending restore → portable move → **unlock** → anything that opens the database. Settings live in the database, so the lock screen's look (skin, dark or light) is copied into `lock.json` when it changes, so the lock screen matches the app.
- **Turning it on and off:** the database is copied into a new encrypted (or plain) file (the library's own copy-with-a-new-key, or `PRAGMA rekey`; which one is settled in the first check), checked by opening it and counting rows in every table, then swapped in; the old file and its `-wal`/`-shm` are deleted. On an SSD, deleted data cannot be guaranteed gone; the help text says so and suggests turning lock on early. *Settled: copy with a new key (`VACUUM INTO`). It happens only at start, at the lock screen, once the password has been entered: turning the lock on in Settings writes `lock.json` and restarts; the database is encrypted when the new password is typed at the lock screen. Turning it off is likewise carried out at the next unlock.*
- **Backups:** an encrypted database gives an encrypted copy, and the backup zip gets `lock.json` too, so a backup opens with the same password or recovery key on any PC (Hello entries are dropped from the zip; they only work on their own PC). The backup label `"DOG AI"` and the `dogai.db` entry name stay as they are. **Restore** must accept all four cases (plain backup into plain or locked DOG.ai; locked backup into plain or locked DOG.ai): a locked backup asks for its own password before staging. Restoring a plain backup into a locked DOG.ai encrypts it while applying, so no plain copy is left behind. `lock.json` is not a machine setting (it travels with the data), but the Hello entries are. *Built: a locked backup restored into a locked DOG.ai is re-encrypted under this DOG.ai's key, so the current password stays; restored into a plain DOG.ai it brings its own lock. The swap at start needs no key; this PC's settings are carried over after the unlock (`DatabaseBackup.FinishRestore`).*
- **Portable mode:** `lock.json` sits in `data\`, so a moved or copied portable folder still opens with the password. `PortableMove` runs after unlock, since it rewrites paths stored in the database.

### Other places text could be written, to check and close

The database holds everything the owner makes (chats, cards, stories, documents' text and vectors, settings), so encrypting it covers almost everything. These are the rest, each to be checked during M8 and listed in Status afterwards as closed or as left:

- **Logs** (`data\logs`): must never hold message, card, document or story text. A quick search finds no logging of message text today; a test will check by running a chat with a marker word and searching the log file.
- **WebView2 folder** (`data\webview`): Blazor Hybrid serves pages from inside the app, so chat text should not reach its cache, but this must be checked by searching the folder for a marker word after a session. If text is found there, the folder is cleared on every lock and exit.
- **Temp** (`data\temp` and the system temp): Whisper, sherpa-onnx and llama-server scratch files; checked the same way, with dictation and reading aloud used during the session.
- **llama-server:** must not be started with any option that saves prompts or slots to disk (checked in `EngineManager`).
- **Exports** (markdown, card files, story exports) are files the owner chooses to write and are left as plain files; the save dialog for a locked DOG.ai says so once.
- **Clipboard:** copied text is the owner's choice; not handled.
